# emerge-ai

AI-ассистированная обёртка над Gentoo `emerge`: исполняет сам `emerge`
(passthrough), а сбои чинит LLM-агент в песочнице, с явным согласием
человека на мутации системы и путём отката. Версия проекта жёстко
привязана к `sys-apps/portage` (совместимость по major.minor).

**Требование: systemd.** Мутационные прогоны (установка, `-a` без `-p`)
на не-systemd хосте отклоняются с кодом выхода 6 — `emerge` не запускается
вовсе. Read-only режимы (`-p/--pretend`, `--changelog`, `--version`/`--help`)
работают и на другом init, с предупреждением в stderr. Агент рекомендует
только `systemctl`/`journalctl`; OpenRC-сценарии не поддерживаются.

Коды выхода: `0` — успех; `3` — portage недоступен; `4` — несовместимость
версий; `5` — отказ от merge без точки восстановления или `--rollback`
без точек/без согласия в неинтерактиве; `6` — не-systemd
хост (мутация отклонена); `7` — гейт автономности запретил merge до мутаций
(fail-closed, включая неписьемый аудит); `130` — оператор прервал
consent-диалог в обычном интерактивном запуске (ноль изменений; в `-a`
отказ, как прежде, завершает прогон кодом `0`); прочее — код возврата `emerge`.

## Установка (Gentoo, личный оверлей)

Ebuild лежит в `packaging/app-portage/emerge-ai/` — live-версия (`9999`,
`distutils-r1` + `git-r3`, один `PYTHON_SINGLE_TARGET` из профиля).

1. Скопировать категорию в личный оверлей:

   ```
   mkdir -p <overlay>/app-portage
   cp -r packaging/app-portage/emerge-ai <overlay>/app-portage/
   ```

2. Сгенерировать Manifest (портage маскирует пакеты локального репозитория
   без него): `ebuild <overlay>/app-portage/emerge-ai/emerge-ai-9999.ebuild manifest`

3. Разрешить live-версию (в ebuild нет KEYWORDS). Широкая маска `**`
   принимает пакет на всех архитектурах — осознанный выбор для live git-r3;
   для одной архитектуры достаточно явного `~amd64`:

   ```
   echo "app-portage/emerge-ai **" | sudo tee /etc/portage/package.accept_keywords/emerge-ai
   # или только для своей архитектуры: echo "app-portage/emerge-ai ~amd64" | sudo tee ...
   ```

4. Установить: `sudo emerge -1av app-portage/emerge-ai`
   (рантайм-зависимости `sys-apps/portage` и `sys-apps/util-linux` подтянутся
   автоматически; `sys-fs/btrfs-progs`/`app-portage/genlop` — опциональны).

   Live-предупреждение: ставится HEAD ветки `master`, а не зафиксированный
   релиз; Manifest локального репозитория генерируется на вашей машине
   (`ebuild manifest`). Для воспроизводимости зафиксируйте коммит —
   `EGIT_COMMIT="<hash>"` в копии ebuild (или патчем оверлея). Известный
   вопрос packaging: `EGIT_BRANCH="master"` должен совпадать с default-веткой
   upstream (в этом репозитории — `master`; при переносе на `main` правится
   ebuild).

После установки:

- конфиг `/etc/portage/emerge-ai.json` (`chmod 0600`, root) создаётся автоматически
  при первой установке, если отсутствует (при обновлениях ваш файл не меняется;
  шаблон — `/usr/share/emerge-ai/emerge-ai.json.default`); задайте в нём `"endpoint"`
  (OpenAI-compatible base URL) и `"model"`; без endpoint каждый LLM-вызов явно
  падает, passthrough-`emerge` при этом работает;
- prompt-правила читаются из `/usr/share/emerge-ai/prompts` (в dev-checkout —
  `./prompts` от CWD; переопределение — env `EMERGE_AI_PROMPTS_DIR`).

## Запуск

```
emerge-ai <любые флаги emerge>
emerge-ai --version     # версия emerge-ai рядом с версией Portage
```

## Собственные флаги

Все прочие аргументы передаются `emerge` дословно.

| Флаг | Действие |
| --- | --- |
| `--noninteractive` | без вопросов в TTY; автономные действия — только rest-tier, остальное fail-closed (лог + ненулевой выход) |
| `--i-understand-what-i-am-doing-and-take-full-responsibility-for-consequences` | полная автономия, включая исполнение отката; короткий псевдоним — `--i-understand-the-risks` (тот же режим, идемпотентно с длинной формой) |
| `--changelog` | дайджест новостей/GLESA/GitHub/git вместо сборки |
| `--rollback` | режим восстановления: список точек, выбор, откат после подтверждения; emerge не запускается (в неинтерактиве нужен флаг ответственности) |

Полностью автоматный прогон (CI, ночной world):

```bash
emerge-ai --noninteractive --i-understand-the-risks -uDN @world
```

## Прогресс прогона и `-v`

По умолчанию прогон не молчит: перед каждым значимым действием emerge-ai печатает
в stderr короткую строку `emerge-ai: ...` — запуск внешней команды с полным argv
(emerge, emaint, btrfs), обращение к LLM (модель, число сообщений, наличие tools),
tool-call агента с аргументами (срезанными до ~200 символов), web-запрос с URL,
правка `package.*`/патча. Строки активности идут только в stderr: stdout остаётся
побайтовым passthrough emerge, коды выхода не меняются; тривиальные read-only пробы
(`findmnt`, `/proc`) строк не порождают.

`-v`/`--verbose` (флаг emerge, передаётся ему без изменений) дополнительно печатает
тело каждого запроса к эндпоинту человекочитаемым блоком — не сериализованным
JSON: первая строка `request:` содержит модель, температуру, число сообщений и
инструментов и размер тела, далее каждое сообщение — отдельной строкой
`emerge-ai:   [№] роль · N символов · превью`, tool-call'ы ассистента — именем с
аргументами `key=value`, результаты инструментов — парами `key=value`, список
инструментов — по строке на инструмент с описанием; вложенные и неизвестные поля
выводятся парами `key=value` с отступом, JSON-синтаксис в дампе не появляется.
Два капа с явными плашками: `…[capped, N chars total]` на текстовое поле
(400 символов) и `dump truncated: shown X of Y lines` на блок целиком
(4000 символов). Длительность вызова печатается, как и раньше, строкой
`LLM answered in ...`. API-ключ в дампы не попадает (значение маскируется,
заголовок `Authorization` не дампится). `-v` также включает вывод рассуждений
модели (агент, сводка дайджеста, news, consent-анализ, сверка config-файлов,
changelog) и живой показ ответа: при `-v` запрос к эндпоинту отправляется
потоком (`stream`), фрагменты рассуждений печатаются в stderr по мере прихода
(блок начинается с `[reasoning] ...`), а основной текст — целыми строками по мере
генерации, с тем же правилом окраски `QUESTION:`; строка о завершении вызова
печатается одна и после всего показанного текста, каждый ход модели показан
ровно один раз (блок `agent proposal:` не дублирует уже показанный текст).
Если эндпоинт не отдаёт поток (не тот `Content-Type`, обрыв до первого
показанного символа), emerge-ai один раз повторяет тот же запрос без стриминга
— при `-v` с одним предупреждением — и продолжает работу как обычно; обрыв
потока уже после показа — ошибка без повтора, чтобы текст не задвоился.
Без `-v` запросы остаются однократными, рассуждения и дампы выключены, вывод —
как раньше. Внимание: verbose-дампы содержат текст логов и конфигов,
отправленный в модель, — они печатаются только в stderr и на диск не пишутся.
В старых конфигах ключ `reasoning_show` игнорируется с предупреждением.

## Перехват `-a/--ask` и `-p/--pretend`

- `-p`/`--pretend`: план исполняет `emerge`, вывод печатается дословно,
  затем emerge-ai добавляет LLM-обогащение плана: детерминированный дайджест
  (tier-распределение, оценка genlop) плюс LLM-сводка «что важно» при
  настроенном `endpoint`; без endpoint или при сбое LLM — только дайджест.
- `-a`/`--ask`: сначала показывается план (как `-p`), затем обогащение,
  затем **consent-диалог emerge-ai** (см. «Диалог согласия»): «merge as-is»
  (`y`) эквивалентен прежнему `Proceed? [y/N]`-«y», abort/EOF — прежнему «n»
  (код выхода `0`, merge не запускается). Слияние после подтверждения
  запускается без `-a`/`-p`. В комбинации `-a -p` (любой порядок,
  включая кластер `-ap`) `--pretend` доминирует: показывается только план,
  вопрос не задаётся, merge не запускается никогда. Без TTY на stdin
  (pipe/скрипт) диалог вырождается в прежний короткий `Proceed? [y/N]`.
- `--noninteractive -a`: вопроса нет; перед merge действует гейт автономности
  (см. «Гейт автономности»), решение логируется в журнал аудита гейта.

## Диалог согласия

Интерактивный мутационный запуск (обычный и `-a`) задаёт **один** вопрос
согласия перед любой мутацией — он заменил и молчаливое создание точки
восстановления в обычном запуске (BREAKING), и бинарный `Proceed?` в `-a`:

- до ответа не создано ничего: сначала печатается контракт точки восстановления
  (вид, путь, исключения `/home/` и т.п., честный текст отката для снапшота vs
  архива, автоудаление после успеха), затем нумерованный список;
- каждый пункт — исполняемый whitelist-сценарий: для чистого плана это только
  merge, для деградированного — починки из находок плана (`package.accept_keywords`,
  etc-update, `emaint --fix world`, `emerge --deselect` — снимает одну запись world-файла мирового члена) плюс
  «merge как есть» с числом нерешённых находок; в формулировке каждого варианта —
  механический текст отмены (копия world, `emerge --noreplace`, удаление строк
  с аудит-маркером `# emerge-ai:`); неисполнимый совет печатается строкой вне
  списка, модель не сочиняет команд;
- номер выбирает сценарий (матрица автономности + аудит как в гейте), `y` —
  merge, `q`/`n`/пусто/EOF/ctrl-c — abort без единого изменения (обычный
  запуск: код `130` и подсказка `--resume`; `-a`: прежний `0`);
- свободный текст уходит модели на разбор последствий (нужен `endpoint`;
  без него — заметка «LLM-разбор недоступен» и меню заново), после применённой
  починки план перечитывается и меню пересобирается; раунды не ограничены —
  диалог заканзует только оператор;
- порядок: consent → создание точки → merge; при abort точка не создаётся.

## Гейт автономности

Перед каждым реальным (не pretend) merge — после consent-диалога или,
в безвопросных запусках, самостоятельно — матрица автономности выносит вердикт
по максимальному тиру плана, и вердикт печатается с обоснованием
(`autonomy gate: ...` в stderr):

- rest-tier (5) — продолжение даже в `--noninteractive`;
- тиры 1–4 в `--noninteractive` — отказ до начала мутаций, код выхода `7`,
  уже созданная точка восстановления вычищается;
- флаг полной ответственности — продолжение на всех тирах с обоснованием;
- вердикты AUTO/DENY пишутся в журнал аудита гейта (`/var/log/emerge-ai/decisions.log`);
  если строка не записалась, в `--noninteractive` это отказ (fail-closed),
  в интерактиве — предупреждение;
- тиры не вычислились (нет плана) в `--noninteractive` — отказ.

## Петля починки после сбоя

При сбое emerge (резолв план-фазы или merge, в любом режиме) печатается proposal
агента, и включается петля «применение → повтор»: через гейт согласия предлагаются
исполняемые варианты — строгий белый список, который emerge-ai строит детерминированно
из класса инцидента (повтор без изменений; повтор с окружением, напр. `ACCEPT_KEYWORDS`;
дописывание строк в `package.unmask`/`package.accept_keywords`; копия пакета в свой
оверлей; команды из закрытого реестра — см. «Команды белого списка»). Текст модели —
только совет оператору: команда из вывода LLM не исполняется никогда.

- Интерактив: пронумерованные варианты, выбранный применяется и исходный сбойный
  вызов emerge повторяется; `[q]`/отказ — система не тронута, предложение осталось
  в выводе, код выхода — код сбоя emerge (как в консультационном режиме).
- Неинтерактив: решает только матрица автономности — rest-tier вариант применяется
  без вопроса с напечатанным обоснованием (`autonomy matrix: ...`), на тирах 1–4
  без флага ответственности — отказ (прежнее консультационное поведение).
- Каждое решение гейта согласия пишется в `/var/log/emerge-ai/decisions.log`;
  если строка аудита не записалась — fail-closed, ничего не применяется.
- Циклов «применение → повтор» не больше 2 на прогон: после второго неудачного
  повтора — финальный отчёт и код последнего сбоя emerge. Применённые циклы
  сохраняются в отчёте прогона (`repair`), точка восстановления до merge живёт
  до успеха — любой применённый вариант снимается каналом отката.
- Без настроенного агента (нет endpoint) петля не включается вовсе: вывод и коды
  не отличаются от консультационного режима.
- Фикс, подтверждённый успешным повтором emerge, записывается в журнал решений
  (см. «Журнал решений»).

## Команды белого списка

Третий род исполняемых действий (наряду с правками `package.*` и копиями оверлея) —
замкнутый реестр команд с фиксированными argv-шаблонами (`whitelist.py`); модель и
находки могут лишь заполнить валидированные слоты, свободная команда/argv не
исполняется никогда. Эмитированные действия исполняют настоящие бинарники через
subprocess — emerge-ai ничего не переизобретает:

- `emaint --check world` — read-only; доступен агенту как инструмент песочницы
  `check_world` (в allowlist read-only команд emaint не добавлен — `--fix` мутирует);
- `emaint --fix world` — перед модификацией создаётся копия
  `/var/lib/portage/world.emerge-ai.<run-id>.bak` (один раз на прогон, не
  перезаписывается); путь копии и текст отмены попадают в строку аудита;
- `emerge --deselect <запись>` — слот = дословная строка world-файла, а не CPV
  находки (версия кандидата превращает команду в `is not a valid package atom`, а
  `=cat/pkg-ver`/чужой слот портage молча не находит и выходит с кодом 0); валидатор
  членства ищет эту строку среди строк world точным совпадением (не по `cat/pkg`), а
  эффект проверяется перечитыванием world-файла: если запись осталась (`no-effect`) —
  это не починка, вариант не попадает в repairs и не предлагается вновь; отмена —
  `emerge --noreplace <запись>`.

Порядок исполнения: повторная валидация слотов (TOCTOU — параллельный прогон мог
изменить world: отказ с сообщением `stale`, без единой записи), бэкап, строка
решения в аудит (`command-execute` с argv, слотами, путём бэкапа и undo-текстом) —
и только затем subprocess. Без записи аудита — fail-closed. Все три действия
подчиняются матрице автономности: в неинтерактиве (и без терминала) новые команды
не выполняются автоматически — остаются советом в отчёте.

Правка `package.*` выбирает файл по фактической раскладке `/etc/portage`: если
`package.<kind>` — каталог (штатная раскладка Gentoo — файлы по категориям),
строка дописывается в `package.<kind>/<category>` по категории атома из строки
(`=dev-libs/jemalloc-5.4.0-r2 ~amd64` → `package.accept_keywords/dev-libs`); если
это файл или отсутствует — дописывается в `package.<kind>`. Раскладка хоста
никогда не переписывается: каталог не заменяется файлом и наоборот. Имя файла
берётся не из имени вида, а из того, что читает portage: правка принятия
лицензий (`accept_license`) пишется в `package.license`, а не в
`package.accept_license`, который portage не открывает. Если
категория из строки не выводится (wildcard `*/*`, set-атом `@world`), строка идёт
в зарезервированный файл `package.<kind>/emerge-ai` того же каталога. Недоступная
цель (на пути не обычный файл, нет прав) — напечатанный отказ
`package-edit refused: cannot write <путь>: <причина>`, а не исключение: в
неинтерактиве такой цикл засчитывается в лимит починок, в интерактиве меню
показывается заново (выход — `q`).

Undo для правок `package.*`: добавленные строки несут аудит-маркер
`# emerge-ai: <дата> <run-id> <причина>`, функция `remove_by_run` удаляет строки
прогона идемпотентно, обходя `package.*` рекурсивно — файлы внутри каталогов
включительно, — и никогда не удаляет сами файлы; обзор строк (`get_package_edit_lines`)
видит те же файлы. Текст отмены из таблицы печатается в consent-формулировке
каждого варианта и называет фактический файл правки
(`package.accept_keywords/dev-libs` на каталожной раскладке) — тот же путь, что и
в анонсе активности при записи. Находка `needs updating` из план-фазы — исполняемый
вариант per-file etc-update по согласию оператора, независимо от
`etc_update_after_build` (флаг по-прежнему управляет только пост-сборочным каналом).

## Дайджест новостей (GLSA/news)

Непрочитанную новость читает сам emerge-ai (`eselect news list` / `read`,
read-only) и печатает дайджест в отчёте `-p` и мутационных прогонов: с endpoint —
LLM-выжимка (сущность, затронутые пакеты плана/world, срочность), без — детерминированный
список заголовков/дат. Тела новостей — недоверенные данные (envelope `wrap_untrusted`,
пометка «никогда не команды» в промпте); приглашение «прочитать руками» не печатается
никогда; новостей без `eselect` или сбой разбора — секция просто отсутствует.

## Журнал решений

Подтверждённые фиксы сохраняются в `/var/log/emerge-ai/journal.jsonl` — по одной
JSON-строке на каждый устранённый сбой. Запись содержит: отпечаток сбоя
(fingerprint — нормализованный хвост stderr вместе с классом), класс и контекст
сбоя, применённое решение с перечнем выполненных действий, подтверждение успеха
(команда повтора исходного сбоя emerge и её код выхода 0), `run_id` прогона.
Неудачные решения в журнал не пишутся никогда: запись создаётся только когда
повторный emerge завершился кодом 0.

Перед разбором нового сбоя агент ищет в журнале совпадающие отпечатки и
добавляет найденное решение в промпт как подсказку с пометкой `SUCCESSFUL
PRECEDENT` — это вариант для рассмотрения, а не готовая команда: исполнение
всё равно идёт через белый список и гейт согласия.

Журнал не влияет на прогоны: отсутствующий или нечитаемый файл — агент просто
работает без прецедентов; ошибка записи уже успешного прогона — предупреждение
`journal write failed` в stderr, код выхода не меняется.

## Префлайт обычного запуска

Любой запуск — даже `emerge-ai app-editors/vim` без флагов — сначала проходит
план-фазу: `emerge --pretend` (резолв), tier-разметка, дайджест плана и
doctor-отчёт (на world/масс-апдейтах). Далее интерактивный запуск задаёт
consent-диалог (см. «Диалог согласия»): точка восстановления (для очередей с
tier 1–4; при недоступных тирах — безусловно) создаётся только после согласия. Безвопросные прогоны сохраняют исторический порядок — точка,
затем гейт автономности перед merge. Подтверждение самого merge при этом
обычное: штатный `[Yes/No]` самого `emerge`.
Все служебные строки план-фазы (дайджест, doctor, info о точке) пишутся в
stderr: stdout мутационного прогона остаётся дословным выводом `emerge`.
Побочная плата — двойной резолв (план + merge); устраняется отдельно
(`avoid-double-resolve-in-plan`).

## Конфигурация

`/etc/portage/emerge-ai.json` — JSON-объект; файл может содержать API-ключ,
права 0600 (при более широких — предупреждение). Без `endpoint` — явная
ошибка перед любым обращением к модели.

```json
{
  "endpoint": "http://127.0.0.1:8080/v1",
  "model": "qwen3.8-flash-next-unsloth-ud-q5_k_xl",
  "api_key": null,
  "language": "auto",
  "show_digest": true,
  "etc_update_after_build": true,
  "changelog_digest": false,
  "agent": {"web_access": true},
  "llm_colors": {"content": "cyan", "reasoning": "dim", "question": "yellow"}
}
```

- `endpoint` — OpenAI-совместимый base URL (`/v1/chat/completions`).
- `model` — имя модели у провайдера.
- `language` — `auto` (из `LC_ALL`/`LC_MESSAGES`/`LANG`) либо явно: код (`ru`,
  `en`, `uk`, `de`, `fr`, `es`) или полное название (`russian`, `english`, ...);
  значение нормализуется к полному имени (`ru`/`ru_RU.UTF-8` → `Russian`),
  неизвестное используется как есть. Директива языка входит во все LLM-вызовы
  с пользовательским выводом: разбор инцидента (агент), сводка дайджеста плана,
  news/GLSA, анализ consent-меню, LLM-сверка config-файлов, changelog-дайджест.
  В структурных JSON-ответах переводятся только human-поля — JSON-ключи и коды
  действий остаются англоязычными. В интерактиве на configured-языке приходят и
  вопросы агента оператору (`ask_operator`: `question`, `label`, `consequences`) —
  язык зафиксирован прямо в описании инструмента; служебные строки интерфейса
  (анонсы, строка выбора, ошибки) остаются на английском, а при английском
  языке промпт и спеки инструментов побайтово идентичны прежним.
- `agent.web_access` — разрешён ли агенту веб-поиск при диагностике (по умолч. вкл).
  При etc-конфигуровке документация подтягивается реально: для путей
  `package.use*/<cat>/<pn>` — страница `packages.gentoo.org`, для прочих файлов —
  поиск по `wiki.gentoo.org`; недоступная сеть = пустой контекст с предупреждением,
  решение LLM всё равно выдаётся.
- `show_digest` — печатать дайджест после успешного мерджа (default true).
- `etc_update_after_build` — разбирать защищённые конфиг-файлы через LLM (default true).
- `changelog_digest` — автоматически строить changelog-дайджест после успешного
  прогона с собранными пакетами (default false; источники обращаются в сеть,
  без `endpoint` — raw-лист; ручная команда `--changelog` работает всегда).
- `llm_colors` — цвета блоков LLM-вывода (см. «Цвет вывода»); допустимы имена
  16 базовых цветов плюс `dim`/`bold`, а также `off`/`null` (выключить);
  невалидное имя — предупреждение и дефолт этого поля.

Неизвестные ключи игнорируются с предупреждением. Старые имена читаются как
алиасы с предупреждением `deprecated`: `post_run_digest` → `show_digest`,
`etc_update_llm` → `etc_update_after_build`, плоский `web_access` →
`agent.web_access`; при конфликте побеждает каноническое имя.

## Цвет вывода

- Цвет включается только когда целевой поток — TTY, `NO_COLOR` не задана и
  `TERM != dumb`; в pipe/файл/CI собственный вывод emerge-ai полностью plain,
  переопределения конфигурацией нет. Собственная окраска emerge передаётся
  как есть — коды ни добавляются, ни удаляются. Так как emerge запускается с
  захваченным выводом (и его auto-режим не увидел бы TTY), emerge-ai сам
  подставляет ему `--color=y`, когда цвет включён и пользователь не задал
  `--color` сам.
- Фиксированная палитра собственных сообщений (не настраивается): ошибки —
  красные, предупреждения — жёлтые, успешный итог — зелёный; строки risk-tier
  в дайджесте плана и doctor-отчёте — градиент от красного (tier 1) до
  приглушённого (высший tier); строки diff `+`/`-` — зелёный/красный;
  вопрос подтверждения — выделение.
- Блоки выбора решений (меню вариантов consent/gate, нумерованные опции
  вопросов агента) явно отделены от текста пустыми строками и баннером
  `── decisions ──…`: тело блока жёлтое, цифры выбора зелёные, баннер —
  жирный жёлтый. Теги типов находок в triage-отчёте и kind-токены дайджеста
  окрашены шкалой важности: красные `severity`, `dep-conflict`, `conflict`,
  `empty-update`; жёлтые `masked`, `dep-required`, `config-updating`,
  `world-file`; циановые `important`, `warning`; прочие типы без цвета.
  Баннер, цвета блока и шкала — фиксированные: `llm_colors` их не перекрывает
  (имену `off` поддаётся только строка вопроса). В pipe/`NO_COLOR` блок
  остаётся отделён баннером и пустыми строками, но без escape-кодов.
- Блоки LLM (ответы модели при `-v`, proposal агента, digest `--changelog`)
  окрашиваются палитрой `llm_colors` (дефолты: `content` cyan, `reasoning`
  dim, `question` yellow). Строки, начинающиеся с `QUESTION:`, получают
  question-цвет — пережиток старой текстовой конвенции вопросов; сам агент
  теперь спрашивает только через интерактивный канал (см. «Вопросы оператора»),
  а `-v` по-прежнему управляет показом рассуждений и к цвету не относится.
- Промпты явно требуют от модели plain text без markdown; emerge-ai не
  рендерит markdown и не вычищает его из ответов постфактум.

## Вопросы оператора

Если для диагноза не хватает факта, известного только оператору (нужен ли
пакет, какую из двух причин чинить), агент задаёт вопрос — но только в
интерактивном запуске: без `-p/--pretend`, без `--noninteractive` и при
TTY на stdin. Во всех остальных режимах инструмента вопросов у модели нет
вовсе (его нет в списке tools), а промпт требует подставить разумное
допущение и перечислить их в секции `ASSUMPTIONS:` итога.

- Один вопрос за раз: 1–6 пронумерованных вариантов, каждый с последствиями
  и уже проверенный `pretend_emerge`; второй вопрос в том же ходе модели
  отклоняется, не израсходовав бюджет.
- Раундов опроса не ограничено (счётчик вопросов снят): гарант выхода —
  сам оператор, а не лимит. Выход `[q]`, пустой ответ или EOF закрывают опрос
  до конца запуска — дальше агент обязан закончить proposal с `ASSUMPTIONS:`,
  зависнуть на вводе невозможно.
- Исполнимый вариант (из белого списка consent-диалога) помечен ключом
  whitelist-а: выбор номера возвращает модели этот ключ, исполнение —
  по-прежнему только за гейтом согласия, после proposal; модель не сочиняет
  ни ключей, ни команд.
- Вопрос, варианты, строка выбора и эхо ответа пишутся в stderr вместе со
  всем выводом агента; цвет — вопрос из палитры `llm_colors`, варианты —
  фиксированный блок решений (жёлтое тело, зелёные цифры, баннер), в pipe всё
  plain. Опрос ничего не меняет в системе: ни
  emerge, ни мерж, ни записи состояния во время вопроса не происходят.
- Ответ оператора (выбор или свой текст через `c`) возвращается модели как
  есть — это доверенный ввод человека, а не вывод внешней команды.

## Исчерпание лимита агентом

Разбор может упереться в лимит: генерация модели обрезана по лимиту токенов/
контекста (`finish_reason == "length"`) или исчерпан бюджет раундов
инструментальной петли. Это не считается сломанным агентом: обрезанный
фрагмент никогда не публикуется как готовый вывод, а усечённые вызовы
инструментов не исполняются.

- Интерактив: агент задаёт вопрос через штатный канал опроса (см. «Вопросы
  оператора») с вариантами «продолжить разбор / свернуть разбор / завершить».
  «Продолжить» возобновляет разбор с точки остановки (то же состояние
  сообщений, увеличенный бюджет раундов) — максимум один раз на разбор;
  «свернуть» — укороченные окна логов и уменьшенный лимит результатов
  инструментов; «завершить» (как и нераспознанный ответ, EOF или `[q]`) —
  итог из накопленных фактов. Второй раз за тот же разбор вопрос не
  задаётся никогда.
- Неинтерактив (флаг `--noninteractive`, не-TTY, `-p`): вопросов нет —
  разбор завершается из накопленных фактов, в
  `/var/log/emerge-ai/decisions.log` пишется аудит-запись (`kind:
  agent-limit`: причина, класс инцидента, `run_id`), в stderr — развёрнутая
  строка `agent limit exhausted (...)`. Коды выхода emerge не меняются.
- Прочие сбои агента (недоступный эндпоинт и т.п.) отделены от лимита и
  ведут себя как раньше: `agent unavailable` / `agent stopped: ...`,
  консультационный режим, код сбоя emerge не тронут.

## Восстановление (rollback)

Перед мержем очереди с tier 1–4 emerge-ai создаёт единую точку восстановления
на запуск — в любом режиме, включая обычный запуск без `-a`/`-p`; в
интерактиве точка создаётся только после consent-диалога (см. «Диалог
согласия»), в безвопросных режимах — до вопросов гейта, как прежде (точка
всё равно живёт до первого merge): read-only btrfs-снапшот
(`/.snapshots/emerge-ai/<run-id>`) либо,
если снапшот невозможен, tar-архив файлов из CONTENTS заменяемых пакетов в
`/var/lib/emerge-ai/archives/<run-id>/` (пользовательские данные `/home`,
`/root`, кэши в архив не попадают). После успешного мержа точки удаляются;
если merge не состоялся (отказ оператора), точка удаляется сразу — при
интерактивном abort диалога согласия она не создаётся вовсе.
Если создать точку не удалось, а в очереди есть tier ≤4 (или тиры недоступны),
мерж блокируется (exit 5), если явно не согласоваться против этого.

Канал отката: разбор последствий → подтверждение → онлайн-восстановление
(tar-архив распаковывается на место); при root в btrfs-подтоме выдаётся
пошаговая инструкция с сохранением снапшота/архива (система не изменена).
`--i-understand-the-risks` подтверждает откат заранее.

После неудачного merge с сохранённой точкой откат предлагается сразу:
с флагом ответственности исполняется автономно (и пишется в журнал запуска),
в интерактиве — вопрос с разбором последствий (отказ ничего не трогает),
в `--noninteractive` — только подсказка, артефакты сохраняются.

Отдельный режим восстановления — собственный флаг `--rollback` (emerge не
запускается никогда, даже с атомами): показ точек восстановления из реестра
(`/.snapshots/emerge-ai/manifest.json` + обход каталогов, рассинхроны
помечаются), выбор (по умолчанию — последняя), затем канал отката. Без TTY
и без флага ответственности — отказ с ручной инструкцией (exit 5);
с флагом ответственности — автономное восстановление последней точки.

## Дайджесты

- После успешного мерджа в stderr печатается дайджест запуска (собранные пакеты +
  действия агента). Опция конфига: `show_digest` (default true).
- `emerge-ai --changelog` — дайджест изменений: локальные новости, GLESA-индекс,
  GitHub releases (`gh_repos`), shallow-клоны (`git_urls`, кэш `/var/cache/emerge-ai/git`);
  при наличии `endpoint` список сокращает LLM до «самого важного», без него — raw-лист.
  С включённым `changelog_digest` тот же дайджест (с фокусом на собранные в прогоне
  пакеты) печатается автоматически после успешного прогона и сохраняется в отчёт
  прогона (`RunState.changelog`).

## Чек-лист ручной верификации на живом хосте (14.2, выполняет пользователь)

Полные команды — в `LIVE_CHECKS.md`; кратко:

- [ ] rest-tier полный цикл без снапшота: `sudo emerge-ai --ask app-misc/<мелкий-пакет>`
      → план+digest → подтверждение → мердж rc=0 → дайджест запуска, снапшот не создавался
      (`btrfs subvolume list /.snapshots | grep emerge-ai` пусто).
- [ ] критичный пакет на btrfs: `sudo emerge-ai --ask sys-apps/<критичный>`
      → снапшот `/.snapshots/emerge-ai/<run-id>` создался; после успеха — удалён;
      при откате-сценарии (`Ctrl+C` до завершения) инструкция восстановлена, снапшот жив.
- [ ] config-protect: пакет с конфигом → показ диффа, LLM-решение с цитатами,
      .pre-emerge-ai бэкап, ._cfg0000_ удалён только после «y».
- [ ] `--noninteractive`: rest-tier чинится сам, критичный — отказ с exit 7
      (гейт автономности до мутаций).
- [ ] Петля починки: сбой merge на живом хосте в интерактиве → выбор варианта `[1]`
      → «applied repair variant» в stderr → повтор emerge; `q` → «consent gate:
      quit — system untouched» и код сбоя; `--i-understand-the-risks` — применение
      без вопроса и строка в decisions.log.
- [ ] `emerge-ai --changelog` — дайджест без падения при недоступных GitHub/git.
- [ ] Префлайт обычного запуска: `sudo emerge-ai sys-apps/<критичный>` → снапшот
      создан до вопроса emerge; `emerge-ai app-misc/<мелкий>` → дайджест/doctor в
      stderr, stdout — только вывод emerge.
