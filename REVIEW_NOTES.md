## H — требует решения

### H1. `-a -p` вместе: после «Proceed? y» запускается РЕАЛЬНЫЙ merge
- `src/emerge_ai/cli.py:361-375`: при комбинации `-a --pretend` фаза плана честно
  отрабатывает в pretend, но после подтверждения `merge_args = drop_flags(emerge_args,
  ASK_FLAGS + PRETEND_FLAGS)` снимает **оба** флага и запускает настоящий merge.
- Нативный `emerge -a -p` merge не запускает никогда (pretend сильнее). README (§«Перехват
  -a/--ask и -p/--pretend») описывает только отдельные `-a` и `-p`, про комбинацию молчит;
  тестов на комбинацию нет (в тестах только `-a` или `-p` по отдельности).
- Риск: пользователь, привыкший к семантике emerge («-p что угодно добавит — всё равно dry-run»),
  получит реальную установку после одного «y».
- Варианты: (а) `-p` побеждает, merge не запускать; (б) документировать и завести тест.
  Первый вариант ближе к принципу наименьшего удивления.

### H2. Гейт автономности/consent-gate (gate.py) не подключён к CLI, но обещан в выводе
- `src/emerge_ai/gate.py` (матрица автономности, `gate()`, аудит в
  `/var/log/emerge-ai/decisions.log`) не импортируется ни одним production-модулем
  (только тесты).
- При этом `cli.py:365-369` в `--noninteractive -a` печатает «tier gate re-checked before
  mutations» — сообщение обещает проверку, которой нет: merge идёт сразу после
  `rollback.protect()`, tier-гейта мутаций нет.
- README:72-73 («гейт risk-tiers сработает на фазе мутаций») и спек `agent-loop-consent`
  («Матрица автономности») тоже описывают это как работающее.
- Фактически единственный работающий «гейт» — interactive `Proceed?` и
  fail-closed на snapshot_required (cli.py:389-402). Для `--noninteractive` без TTY
  автономные мутации tier 1-4 проходят без аудита вообще.
- Сюда же: `tiers.noninteractive_auto_allowed` (tiers.py:157) не вызывается ни из одного
  production-модуля (только тесты) — «матрица автономности» спека живёт только на бумаге.

### H3. Канал отката не выведен в CLI
- `rollback.rollback(...)` (`src/emerge_ai/rollback.py:135`: последствия → подтверждение →
  восстановление) не вызывается из cli. Наружу торчат только `protect` (cli.py:80) и
  `cleanup` (cli.py:414).
- README §«Откаты» и спек `system-rollback` («Откат по решению пользователя»,
  «Недоступный онлайн-откат») описывают работающий канал; в CLI нет ни флага
  (`--rollback`), ни предложения отката после инцидента/неудачного мерджа критичного пакета.
- Последствие: снапшот/архив создаются, но штатно восстановить систему из них нельзя —
  только руками по инструкции. Снапшот к тому же удаляется после успеха (это по спеке, ок).
  Ветка спека «Недоступный онлайн-откат» (сохранить снапшот + инструкция,
  rollback.py:141-166) недостижима из CLI по той же причине — общий вход `rollback.rollback()`.

### H4. Журнал прецедентов никто не пишет
- `journal.record`/`journal.finalize` (`src/emerge_ai/journal.py:41,53`) не вызываются из
  production-кода; читают журнал только `IncidentAgent` для дедупа вопросов
  (`agent.py:400-401` → `journal.find`).
- Спек `agent-loop-consent` («Журнал только успешных решений») требует запись после
  успешного применения фикса и поиск по отпечатку перед разбором. Дедуп вопросов сейчас
  всегда промахивается — журнал пуст всегда.
- Связано с H5: писатель живёт в неиспользуемом `run_agent`.

### H5. Полный цикл агента `run_agent` (propose→gate→apply) не подключён
- `agent.run_agent` с консент-гейтом, применением вариантов, рераном emerge и защитой от
  рекурсии вызывается только из тестов. В production `cli._call_agent_fn` дёргает лишь
  advisory-`IncidentAgent.propose` — предложение печатается, ничего не применяется.
- Это осознанная «advisory-фаза» или незавершённая проводка? Если второе — H2/H3/H4/H5
  один большой незакрытый логический блок (группы spec agent-loop-consent), и стоит
  завести OpenSpec-изменение на доводку; если первое — подправить README/сообщения,
  чтобы не обещали автономию, которой нет.

### H6. Обычный запуск (без `-p`/`-a`) минует план-фазу: ни снапшота, ни doctor, ни дайджеста
- `cli.py:310-324`: если нет ни `--pretend`, ни `--ask`, emerge-ai сразу гонит merge
  через `run_emerge_capturing` — без классификации тиров, без `rollback.protect()`,
  без doctor-префлайта и без tier-дайджеста (всё это живёт только в план-ветке).
- Спек `system-rollback` «Триггер защиты перед установкой» НЕ обусловлен флагом `-a`:
  «SHALL создавать точку восстановления перед первым merge, если в очереди есть tier 1–4».
  Значит `emerge-ai sys-libs/glibc` (без флагов) нарушает спек: merge пройдёт без
  recovery point. Спек `run-reporting` «Автоматический doctor» тоже нарушается
  дословно: его сценарий — `emerge-ai -uDN @world` без `-a`/`-p`, а `doctor_report`
  вызывается только из план-ветки (cli.py:353-355).
- Интерактивный `Proceed?` при этом остаётся — его задаёт сам emerge по умолчанию,
  так что «неожиданной» установки нет; проблема именно в отсутствии защиты/информирования.
- Починка: вынести план-фазу (pretend-резолв → тирование → protect → doctor) на общий
  путь перед любым мутационным запуском; `-p`-вывод при этом уже печатается штатно.

## M — расходится с заявленным / заметные дефекты

### M1. web_fetch-заглушка в etc-flow игнорирует файл
- `cli.py:176-178`: `def web(path, ...)` не использует `path` и всегда тянет
  `https://wiki.gentoo.org/` (главную страницу). При `web_access: true` LLM получает
  нерелевантный мусор вместо документации по пакету. Заглушка из ранней группы —
  либо реализовать (извлечь категорию/пакет из `new_path` → `https://packages.gentoo.org/packages/<cat>/<p>`
  + поиск вики), либо отключить и честно сказать «не реализовано».

### M2. stderr emerge сливается в stdout на всех путях — закрыто (change `split-emerge-stderr`)
- `runner.run_emerge_capturing` (`runner.py:40`) ставит `stderr=STDOUT`; mirror идёт в
  `sys.stdout`. Значит и на raw-passthrough пути (без `-p/-a`) stderr emerge попадает в
  stdout emerge-ai: ломаются `emerge-ai ... 2>/dev/null`, разделение в пайплайнах,
  и «байт-в-байт passthrough stdout» (спек console-output) перестаёт быть правдой для
  строк, которые emerge пишет в stderr.
- Компромисс захвата неизбежен (буфер нужен для incident/enrich), но стоит хотя бы
  задокументировать; лучше — писать stderr-строки в `sys.stderr` (детект по префиксам
  тяжело, но можно не мержить, а читать два потока двумя потоками чтения).

### M3. `text=True` без `errors="replace"` при захвате вывода emerge — закрыто (change `lenient-emerge-decoding`)
- `runner.py:36-46`: декодирование строгое; не-UTF-8 байты в выводе emerge (редко, но
  бывает в ebuild-сообщениях/именах) уронят `UnicodeDecodeError` посреди зеркального
  вывода. Дешёвый фикс: `errors="replace"`.

### M4. «LLM-обогащение плана» на самом деле без LLM
- README:66-67 и спек run-reporting («Enrich для pretend/ask»: «добавить обогащение от
  LLM») обещают LLM-обогащение; реализация — детерминированный `plan_digest`
  (tier-распределение + genlop-оценки, `enrich.py:52+`). LLM в фазе плана не участвует.
  Либо формулировки смягчить («дайджест с оценками времени»), либо добавлять LLM.

### M5. `--i-understand-the-risks` — фантомный флаг
- Упоминается в `gate.py:53,61,68` (и, следовательно, в спеке agent-loop-consent),
  но не парсится в `flags.py` и не читается в cli. Если пользователь его передаст —
  уйдёт в emerge как неизвестный параметр. Либо добавить в OWN_FLAGS (и связать с
  `mode.responsibility`/гейтом), либо убрать упоминания.

### M6. `confirm_fn` в `_etc_flow` — декоративный параметр — закрыто (change `fix-etc-confirm-fn`)
- `cli.py:145` принимает `confirm_fn`, но внутри нигде не использует: человек-гейт идёт
  через `input_fn` (deфолт — встроенный `input`, injectable), а `apply_decision` получает
  `lambda _p: True` (cli.py:196). Вызывающий код (`confirm_fn=confirm` в cli.py:421)
  создаёт ложное впечатление, что поданная функция что-то решает. Убрать параметр или
  использовать.

### M7. Hook-слот `hooks.set_hook` никем не выставляется — закрыто (change `remove-enrich-hook`)
- `hooks.py` — слот для enrich-колбэка; в production `_hook` всегда `None`,
  `run_hook` no-op (cli вызывает его «в пустоту»). Мёртвая индирекция: либо убрать,
  либо wired (богаче — но тогда дублирует прямой вызов plan_digest).

### M8. Слот `runner.run_emerge` (чистый passthrough) не используется — закрыто (change `remove-unused-run-emerge`)
- `runner.py:13-15` — ни одного вызова в src и тестах (все идут через
  `run_emerge_capturing`). Мелочь, но «emerge never replaced» лучше подтверждать одним
  путём исполнения.

### M9. Спек «Поддержка только systemd» не реализован (и, похоже, сам спорен)
- `cli-compat` требует: только systemd, рекомендации через systemctl, без openrc-сценариев.
  В коде нет ни одной проверки init-системы; инициализация лишь определяется для
  контекста промпта через `/proc/1/comm` (prompts.py:71, при недоступности — «unknown»).
- Sandbox-allowlist содержит `journalctl`, но не имеет аналога для OpenRC-хостов
  (rc-service/rc-log) — на OpenRC-машине агент фактически слеп к системному логу
  (в jail только /var/log/portage). При этом tier-hints и prompts/rules трактуют
  openrc и systemd равноправно (tiers.py:25-26, rules/30-tiers.md), README о init молчит.
- Для Gentoo «только systemd» выглядит ошибкой спека (OpenRC — основной init).
  Скорее править спек на «init-aware», чем код на systemd-only; но полумеры надо закрыть.

### M10. Схема конфига расходится со спеком; опции changelog нет вовсе
- Спек `config-prompts` задаёт ключи `show_digest`, `etc_update_after_build`,
  `changelog_digest`, `agent.web_access`; в `DEFAULTS` (config.py:15-26) — 
  `post_run_digest`, `etc_update_llm`, плоский `web_access`, и никакого changelog-ключа.
  `_REMOVED_KEYS` (config.py:28-30) знает только про `reasoning_show`, так что конфиг,
  написанный по спеку, засыплет вывод «ignoring unknown key» и молча не применит опции.
- Либо переименовать ключи с алиасами (и обновить default-конфиг пакета), либо править
  спек. Заодно см. M11 про changelog.

### M11. Changelog-дайджест — только ручная команда `--changelog`
- Спек `run-reporting` «Changelog-дайджест собранных пакетов» подразумевает обогащение
  по пакетам, собранным в прогоне (и опцию `changelog_digest`). Реализованы источники и
  LLM-отбор (changelog.py:19-140), но вызов — только ручной флаг (cli.py:296-297);
  `post_run_digest` changelog не дёргает, опции конфига нет. Частично реализовано.

### M12. Язык обоснований etc-update не подключён
- Спек `etc-update-llm` «Язык обоснований»: разбор config-файлов — на языке конфига.
  В `etcupdate.py` слово `language` не встречается вообще: `ETC_SYSTEM`/`build_merge_prompt`
  (etcupdate.py:60-90) не содержат языковой директивы, `cli._etc_flow` не передаёт
  `cfg.resolved_language()`. На практике LLM угадывает язык по контексту — негарантированно.
  Язык подключён только в промпте агента (prompts.py:94).

### M13. Исчерпание лимита токенов/раундов не обработано по спеку
- Спек `agent-loop-consent` «Исчерпание лимита токенов»: в интерактиве — вопрос
  оператору с вариантами, в неинтерактиве — лог+завершение. Реальность: `finish_reason`
  сохраняется (llm.py:26,90), но потребителей нет; превышение раундов — `LLMError`
  (llm.py:147), которое `_maybe_agent` глушит в одну строку stderr (cli.py:140-142).

  world-блока есть.
