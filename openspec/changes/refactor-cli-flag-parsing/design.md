# Design

## Context

Разбор опций сейчас распределён по трём модулям и содержит находки ревью (см. proposal.md — Why):

- `flags.py`: `OWN_FLAGS` — кортеж-константа, в `parse_own_flags` флаги сопоставляются по индексу (`OWN_FLAGS[1]`, `OWN_FLAGS[2]`); та же строка флага продублирована в `OWN_FLAG_HELP` (уже с расхождением выравнивания).
- `cli.main()`: мета-флаги `--version`/`-V`/`--help` распознаются инлайн только на позиции `argv[0]`; перехват `--resume` — инлайн-блок «нашёл/вырезал/продолжил или свежий run», причём в ветке «нет run'а» флаг теряется и emerge стартует без аргументов.
- `runner.py`: `flag_present`/`drop_flags` работают корректно (кластеры коротких флагов), но `_flag_kinds` возвращает безымянный `tuple[set, set]` — неочевидно, что где.
- `state.new_run(argv, mode)` принимает и `Mode`, и `dict` (тесты передают dict) — тип результата парсинга размыт.

Ограничения: D1 из archived design — emerge никогда не подменяется, argv кроме собственных флагов проходит насквозь; собственные флаги не должны «съедать» аргументы emerge; порядок мета-флагов относительно version-gate уже сложился (мета-флаги и changelog до гейта).

## Goals / Non-Goals

**Goals:**
- Единый источник истины для собственных флагов (код = help = парсер).
- Явные именованные хелперы для «магических» правил main() с docstring'ами, документирующими позицию-0 и resume.
- Фикс resume-passthrough + регрессионные и characterization-тесты.
- Строгий тип `Mode` во всех границах.

**Non-Goals:**
- Не декомпозировать остальные фазы `main()` (direct/plan/ask-merge) — согласовано с пользователем, отдельный будущий change при необходимости.
- Не менять `flag_present`/`drop_flags` семантически; не переходить на `argparse`.
- Не менять набор и поведение самих флагов, коды выхода, формат runs-JSON.

## Decisions

### D1. Табличный парсер вместо positional-кортежа и вместо argparse
`flags.py` получает маппинг `OWN_FLAGS: dict[str, str]` («флаг → имя поля `Mode`»), например `{"--noninteractive": "noninteractive", ...}`. `parse_own_flags` делает `attr = OWN_FLAGS.get(arg)` (точное совпадение покрывает «не по префиксу» бесплатно) и `setattr(mode, attr, True)`. `OWN_FLAG_HELP` строится функцией из таблицы (фикс-колонка описания; длинный флаг responsibility, как сейчас, с переноса).
Альтернативы: (a) три именованные константы вместо цикла — дешевле, но help по-прежнему дублируется вручную; (b) `argparse.parse_known_args` — отвергнуто: произвольный argv emerge (кластеры `-av`, `--usepkg=y`, атомы) конфликтует с аббревиатурами и ошибками argparse, а D1 требует «strip-and-passthrough», а не «парсить argv».

### D2. Хелперы мета-флагов и resume в cli.py
- `_meta_command(argv) -> int | None`: возвращает код выхода, если `argv[0]` — `--version`/`-V`/`--help` (логика `_version_text` + печати `OWN_FLAG_HELP` переезжает внутрь); иначе `None`. Docstring фиксирует правило «только первый аргумент — режим запуска; в остальных позициях флаг принадлежит emerge».
- `_resolve_resume(emerge_args, mode, runs_dir) -> tuple[state.RunState, list[str]]`: возвращает (run, emerge_args). Найден незавершённый run → `(run, emerge_args без --resume)`; не найден → `(state.new_run(emerge_args, mode), emerge_args как есть)`. Оба сообщения (`resuming`/`starting fresh`) печатаются внутри.
Альтернатива: оставить в main() с комментариями — отвергнуто: цель ревью — чтобы правило читалось из имени функции, а не из комментария.

### D3. Resume-passthrough = обычный запуск
При отсутствии resume-able run'а `--resume` остаётся в argv, создаётся новый run (как делал и раньше), дальше стандартный поток (pretend/ask/direct). Побочный эффект: на таком запуске работают обогащение и incident-обработка — это согласуется с «emerge-ai как тонкая надстройка» и проще, чем выделенная exec-ветка без run-записи. Зафиксировано в спеке (см. delta, «Нет run'а emerge-ai — passthrough emerge»).

### D4. `Mode` как единственный тип границы
`state.new_run(argv, mode: Mode)`; ветка `dict(mode)` и локальный импорт `Mode` удаляются. `tests/test_cli_integration.py:57,141` переводятся на `Mode(...)`. Альтернатива — оставить dict для тестов: отвергнуто, тесты должны гонять реальный тип.

### D5. Обход version-gate режимами без portage-API — фиксируется, не чинится
`--version`/`--help`/`--changelog` выполняются до `_compat_gate()` (текущий код). Changelog-digest не использует python-API portage и не запускает emerge, поэтому exemption признаётся намеренным и заносится в спеку новым сценарием (см. delta «Обходят проверку»), а не переносом гейта в начало `main()`.

### D6. Стратегия тестирования: characterization → refactor → фикс
Сначала добавляются characterization-тесты на текущее поведение (точное совпадение own-флагов, позиция 0 для мета-флагов, идемпотентность повтора, help без `--changelog`-расхождения), которые passing ДО рефакторинга. Затем рефакторинг (тесты не должны сломаться). Затем фикс resume — его регрессионный тест новый и краснеет до фикса.

## Risks / Trade-offs

- [Изменение наблюдаемого поведения `emerge-ai --resume` без run'а] → зафиксировано сценарием спеки + регрессионным тестом `test_cli_integration`; в README секции про `--resume` нет (проверено grep-ом), расхождений документации не остаётся.
- [Дикционарная таблица флагов позволяет опечатку в имени поля `Mode`] → тест сверяет `set(OWN_FLAGS.values()) == {f.name for f in dataclasses.fields(Mode)}`.
- [Characterization-тесты случайно закрепят баг (например, потерю `--resume`)] → тесты на resume-ветку пишутся только под новую семантику; старая поведение-ветка удаляется вместе с фиксом.
- [Удаление dict-ветки `new_run` — скрытые вызовы] → grep: единственный источник dict — два места в тестах; обновляются там же.

## Migration Plan

Совместимость сохраняется для всех существующих сценариев, кроме зафиксированного фикса resume; миграции данных/конфига нет; откат — revert commit'а(ов) change целиком.
