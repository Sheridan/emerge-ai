# Design

## Context

Мотивация — в proposal.md (Why). Состояние кода:

- `LLMClient.render(resp, stream)` печатает `[reasoning]` (при флаге `show_reasoning` и
  непустом `reasoning_content`, цвет `llm_colors.reasoning`) + content через
  `paint_llm_block`. Единственный потребитель — `run_tool_loop` (agent-петля), куда `cli`
  передаёт `render_to=sys.stderr` под `-v`.
- Прямые `client.chat()`-вызовы (`etcupdate.llm_decide`, `consent_analyze` в `cli`,
  summarize/news-сводки, `changelog.llm_digest`) выбрасывают `Response.reasoning`.
- Эндпоинт (локальный strata, llama.cpp-семейства) отдаёт `reasoning_content` по умолчанию —
  запрос дополнительных параметров thinking не требует; проверено живым запросом.
- `_post_run_digest` (`cli.py`) строит changelog-`LLMClient(cfg)` без флага verbose —
  единственный LLM-клиент, до которого `-v` не доходит.

## Goals / Non-Goals

**Goals:**

- Ровно одна точка печати рассуждений, покрывающая все существующие и будущие вызовы.
- Отсутствие дублей: tool-цикл показывает каждое рассуждение один раз.

**Non-Goals:**

- Строки анонсов/дампы запросов (`add-progress-logging`); язык (`fix-llm-response-language`);
  параметры запроса thinking (эндпоинт отдаёт рассуждения без них — не трогаем payload);
  стриминг рассуждений по токенам.

## Decisions

### D1. Печать в `chat()`, а не в call-site'ах

`LLMClient.chat()` после парсинга ответа печатает `[reasoning]` (флаг конструктора +
непустое поле; палитра и plain-в-pipe — как сейчас в `render`). Каждый обращённый к модели
код получает видимость автоматически, включая будущие новые места.
Альтернатива — добавить `client.render` в каждый прямой вызов: отвергнута, именно «забыли в
одном месте» и есть корень бага; новые места забудут снова.
Альтернатива — callback-слухатель ответов: отвергнута, лишняя индирекция при единственном
потребителе.

### D2. `render()` — только content; `run_tool_loop` не меняется

Чтобы tool-цикл не напечатал рассуждение дважды (`chat` уже напечатал, `render` печатал
ещё раз), `render()` теряет reasoning-ветку. Контракт `run_tool_loop`/`render_to` остаётся
прежним: content каждого хода — как сегодня.
Альтернатива — оставить печать в `render`, а `chat` обходить флагом: отвергнута, два
режима одного метода — источник будущих расхождений.

### D3. Поток и оформление без изменений

stderr, префикс `[reasoning]`, цвет `llm_colors.reasoning` (бледнее content), plain в pipe —
spec: console-output остаётся; тесты палитры `test_llm.py` переносятся на новый seam.

## Risks / Trade-offs

- [Печать в `chat()` трогает `test_llm.py`, ожидавший тишины] → фикстуры обновляются тем же
  коммитом; поведение «без -v тихо» остаётся покрытым.
- [Кто-то использует `render()` ради reasoning напрямую] → единственный потребитель в
  репозитории — `run_tool_loop`; внешний API не декларируется.
- [Пересечение по файлу `llm.py` с `add-progress-logging`] → изменения в разных частях
  `chat()` (печать ответа vs анонс/дамп запроса); конфликты — текстовые, тривиальные.

## Migration Plan

Нет изменений конфига/состояний; откат — откат коммита (thinking снова виден только в
agent-петле).
