# Design

## Context

Сейчас цикл обрывается на предложении: `_maybe_agent` (cli.py:106-142) печатает
`AgentResult.proposal` (agent.py:232-236) и не имеет канала применения. Готовые
кирпичи: `gate.gate(variants, mode, confirm_fn, ...)` возвращает
`{status: applied|denied|declined|quit, ...}` и перед любым `variant.action()` пишет
аудит (gate.py:84-136, 73-81); `autonomy_decision` по флагам `mode` решает
AUTO/ASK/DENY (gate.py:48-71). Интерактивность запуска уже вычислена в cli
(cli.py:307-308) и прокидывается в агента. Состояние INCIDENT → MERGE легально
(state.py:28-29). Точка восстановления к моменту сбоя уже создана и не вычищена
(очистка только при rc=0, cli.py:413-414).

## Goals / Non-Goals

- Goals: довести предложение до проверяемого применения; не менять advisory-поведение
  при отказе; не изобретать новый канал мутаций — только `gate.gate` + штатный runner.
- Non-Goals: откат из CLI (wire-rollback-channel), общий tier-гейт перед первым
  merge (wire-autonomy-gate / plan-before-plain-merge), запись журнала (wire-journal-writer),
  свободные shell-команды модели.

## Decisions

- **D1. Оркестрация в CLI, а не в агенте.** Новый seam `_incident_flow(run, proposal,
  ...)` в cli.py вызывает `gate.gate` и повтор merge; `IncidentAgent` остаётся
  read-only (спека: песочница агента). Альтернатива — `run_agent` внутри agent.py,
  который дёргает runner: агент получил бы доступ к мутациям и его sandbox-гарантия
  перестала бы быть инвариантом модуля.
- **D2. Исполняемые варианты — типизированный белый список.** Варианты строятся из
  структурированной части ответа агента (kind + параметры) и покрывают действия, для
  которых уже есть реализация (правка accept_keywords/use через config_edit, латка
  через overlay/ladder, повтор pretend); произвольный текст модели в `action` не
  попадает. Альтернатива — генерировать shell-команды: отвергнута из-за
  prompt-injection (тот же мотив, что у read-only песочницы).
- **D3. Лимит повторов = 2 на прогон.** После второго неудачного повтора — финальный
  отчёт и код emerge, как сейчас. Альтернатива «повторять до успеха» зацикливает на сбоях,
  которые не чинятся вариантами агента (fetch, место на диске), и удваивает время прогона.
- **D4. Отказ = текущее поведение.** `declined`/`quit`/`denied` из гейта ничего не
  меняют: предложение уже напечатано, код выхода и отчёт не отличаются от
  сегодняшних. Альтернатива «deny в неинтерактиве меняет код выхода» оставлена
  wire-autonomy-gate (там решение принимает матрица до мутаций, а не после сбоя).
- **D5. Согласие в неинтерактиве — только матрица.** `mode` из флагов CLI передаётся
  в гейт как есть (gate.py:48-71); собственных поблажек петля не вводит. Флаг
  `--i-understand-the-risks` заводит wire-risk-flag.

## Risks / Trade-offs

- [Применённое действие ухудшает состояние] → только белый список действий с
  pretend-проверкой варианта до показа (базовая спека), аудит каждого решения,
  сохранённая точка восстановления до первого apply.
- [Повтор merge снова падает и пользователь получает два длинных вывода] → между
  попытками печатается разделитель с обоснованием повтора; лимит D3.
- [Несогласованность с wire-autonomy-gate: два места вызывают гейт] → общий вызов
  `gate.gate`, изменение только добавляет вызовы; порядок landing: сначала эта петля,
  гейт на mutate-пути добавит соседнее изменение.
