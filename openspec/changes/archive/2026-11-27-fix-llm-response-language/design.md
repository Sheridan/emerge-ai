# Design

## Context

Мотивация — в proposal.md (Why). Состояние кода:

- `Config.resolved_language()` нормализует только `auto` (в «russian»/«english»); явные
  значения возвращает как есть (`"ru"` → `"ru"`).
- `_maybe_agent` (`cli.py`) передаёт в `collect_context` сырое `cfg.language`, минуя
  резолв; `assemble_system_prompt` печатает «Always respond in {language}» инлайн-строкой.
- Прямые `chat()`-вызовы без директивы языка: сводка дайджеста
  (`enrich.PLAN_SUMMARY_SYSTEM`), анализ consent-меню (`consent.CONSENT_ANALYSIS_SYSTEM`),
  changelog-дайджест (`changelog.CHANGE_SYSTEM`). Уже получают язык и корректно работают:
  news (`language=cfg.resolved_language()`), etc-update (структурный промпт с хвостом
  «JSON keys and action codes stay exactly as specified»).
- Формат ответа части вызовов — структурный JSON (дайджест-сводка, consent, etc-update):
  ключи и коды парсятся детерминированно и сдвинуться не должны.

## Goals / Non-Goals

**Goals:**

- Одно место нормализации языка и один хелпер директивы; ни один пользовательский
  LLM-вызов не может «забыть» про язык.
- Совместимость: структурные ответы продолжают парситься после смены языка вывода.

**Non-Goals:**

- Локализация самого интерфейса emerge-ai (строки, дайджесты, сообщения) — только вывод
  модели.
- Новые ключи конфига; перевод prompt-правил `/usr/share/emerge-ai/prompts`.

## Decisions

### D1. Нормализация в `resolved_language()` — единственная точка

Срез региона/кодировки (`split` по `_`, `-`, `.`), таблица кодов → полные названия
(ru→Russian, en→English, uk→Ukrainian, de→German, fr→French, es→Spanish +Common),
неизвестное значение — как есть (spec), `auto` — та же нормализация из
LC_ALL/LC_MESSAGES/LANG с фолбэком English. Все call-site'ы (`_maybe_agent`, news,
etc-update, новые проводки) вызывают только `resolved_language()`.
Альтернатива — нормализация в каждом билдере промптов: отвергнута, разъезд гарантирован.

### D2. `prompts.language_directive(language)` с структурным вариантом

Общий хелпер: обычный — «Always respond in X unless the user asks otherwise.»; структурный
(`structured=True`) — плюс хвост «JSON keys and action codes stay exactly as specified»
(паттерн etcupdate переезжает в хелпер). `assemble_system_prompt` использует хелпер вместо
инлайн-строки. Промпт-правила не переводятся — модель ведёт диалог на целевом языке,
правила остаются англоязычными данными промпта.
Альтернатива — центральная инъекция system-сообщения в `LLMClient.chat()`: отвергнута,
структурные промпты несут собственный контракт, дубль на каждый ход tool-цикла, риск
конфликта директив.

### D3. Язык — параметр билдеров промптов, а не клиента

`enrich.build_plan_summary_messages`, `consent.build_analysis_messages`,
`changelog.llm_digest`/`collect_digest` получают параметр `language` (значение — из
`cfg.resolved_language()` в `cli`). Клиент `LLMClient` о языке не знает: промпт остаётся
полностью собранной единицей, тесты билдеров проверяют директиву без HTTP-слоя.
Альтернатива — язык в конструкторе клиента: отвергнута, неявная магия на каждый вызов,
плохо тестируется и ломает переиспользование клиентов.

## Risks / Trade-offs

- [Модель упорно игнорирует директиву] → нормализованное полное название снижает риск;
  live-проверка в LIVE_CHECKS фиксирует фактическое поведение endpoint'а.
- [Смена языка сдвинет парсинг структурных ответов] → структурный вариант директивы
  фиксирует ключи; юниты парсеров с русскоязычным human-полем.
- [Англоязычный дефолт станет регрессией] → тесты: `language` отсутствует / `en` — промпт
  не меняется, директива English явная.

## Migration Plan

Схема конфига не меняется; значения `language` из существующих конфигов читаются как прежде
(код `ru` теперь просто разворачивается в директиву). Откат — откат коммита без миграций.

## Open Questions
