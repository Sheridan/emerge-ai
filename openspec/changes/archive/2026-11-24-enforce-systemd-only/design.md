# Design

## Context

- Спек `cli-compat` «Поддержка только systemd» (openspec/specs/cli-compat/spec.md:75-80) обязывает systemd-only рекомендации; проверка init в коде отсутствует (M9, REVIEW_NOTES.md:145-154) — init читается только как контекст промпта (`prompts.py:71`, fallback «unknown»).
- Агентский канал лога — `journalctl` (`sandbox.py:18` allowlist, `sandbox.py:117` исполнение, `agent.py:94` описание инструмента); на OpenRC агент слеп к логу сервиса, в jail только `/var/log/portage`.
- `tiers.py:25-26` и `prompts/rules/30-tiers.md:2` называют openrc наравне с systemd — но это критичность пакета, а не управление сервисом.
- Коды выхода CLI: 3 — portage недоступен, 4 — несовместимая версия (`cli.py:42-50`), 5 — сорванная защита (`cli.py:408`); мета-флаги и `--changelog` работают без portage и без emerge.

## Goals / Non-Goals

**Goals**
- Спек становится исполняемым: мутационный запуск на не-systemd невозможен незаметно — явный отказ до первого запуска emerge.
- Read-only сценарии (план, changelog, `--version`/`--help`) остаются работоспособными где угодно — с предупреждением.
- Промпты/доки говорят одним языком со спеком (systemd-only), openrc-сценарии не формируются.

**Non-Goals**
- Не делать init-aware/OpenRC-поддержку (решение пользователя: спека остаётся «только systemd»).
- Не добавлять `rc-service`/`rc-log` в sandbox и не менять tier-hints.
- Не трогать механику защиты/отката (смежные изменения).

## Decisions

**D1. Детект — канонический признак boot `is_systemd()`: существует `/run/systemd/system`, fallback — `/proc/1/comm == "systemd"`; неизвестное состояние трактуется как «не systemd» (fail-closed).** Новый модуль `init_check.py` с инъективными зондами (как `btrfs_fn`/`run_fn` в rollback/runner) — тесты подменяют зонды напрямую. Альтернатива (только `/proc/1/comm`, как в prompts) отвергнута: PID 1 может называться `init` при systemd-сборе, детект ложно отказывает.

**D2. Гейт — в `cli.main` после разбора собственных флагов, до входа в мутационный путь; отказ — новый код выхода 6.** Класс режима: мутация (plain, merge-продолжение `-a`) → не systemd → `ui.err` с текстом «поддерживаются только systemd-системы, обнаружен <init>» + rc 6, emerge не запускается ни разу. Read-only (`-p` solo, `--changelog`, мета-флаги) → однократное предупреждение в stderr, работа продолжается. Альтернатива (переиспользовать rc 4 «версия несовместима») отвергнута: скрипты различают типы окружения по коду.

**D3. Режим `--rollback` (после `wire-rollback-channel`) — предупреждение, а не отказ.** Восстановление снапшота/архива (btrfs/tar) от init не зависит, и блокировать recovery на неподдерживаемом хосте — значит оставить систему без пути отката. Альтернатива (полный отказ) отвергнута: остаться без recovery хуже, чем с неподдерживаемым init.

**D4. Тексты: директива в `prompts/rules/00-role.md`/`10-safety.md` («системные действия и рекомендации — только systemctl/journalctl; openrc-команды не предлагать»); sandbox остаётся как есть.** `journalctl` в allowlist не трогаем, openrc-эквиваленты не добавляем — канал, которого нет по спеку, агенту не отдаём. `tiers.py`/`rules/30-tiers.md` не правим (критичность ≠ init-рекомендации). Альтернатива (правка tiers) исказила бы риск-модель OpenRC-хостов, где openrc критичен как пакет.

**D5. Обходного флага (`--allow-non-systemd`) не заводим** —fail-closed-конвенция проекта; запрос на OpenRC = отдельное изменение спека, а не escape hatch в CLI.

## Risks / Trade-offs

- [CI/контейнеры без systemd: тесты и пайплайны отвалятся на мутационных путях] → все CLI-тесты инжектят systemd-зонд по умолчанию; реальные контейнерные прогоны — read-only режимы (предупреждение, не отказ).
- [Ложный отказ на экзотической сборке (read-only /run, имя PID1)] → двойной сигнал (каталог + comm) и ясное сообщение с обнаруженным init; оператор видит причину, а не молчаливый пропуск.
- [Пользователи OpenRC теряют рабочий сейчас путь] → сознательное сужение (решение зафиксировано в M9-обсуждении); отказ явный и объясняющий, в README указан prerequisite.
- [Гейт в `cli.main` пересекается с pre-merge блоком `plan-before-plain-merge`] → гейт — отдельный вызов до блока, порядок «гейт инициализации → гейт версии → pre-merge»; конфликтные строк минимум.
