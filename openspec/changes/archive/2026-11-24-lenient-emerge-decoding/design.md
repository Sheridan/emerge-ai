# Design

## Context

- `run_emerge_capturing` (`runner.py:32-50`) использует `subprocess.run(text=True)`; при захвате строки декодируются в UTF-8 с политикой `strict`, и `UnicodeDecodeError` обрывает зеркальный вывод до получения кода возврата. REVIEW_NOTES M3 (`REVIEW_NOTES.md:111-114`) предлагает дешёвый фикс `errors="replace"`.
- `run_emerge` (`runner.py:14-16`) — raw-passthrough: stdio наследуется, байты не читаются, изменения его не касаются.
- Изменение `split-emerge-stderr` переписывает ту же функцию на два байтовых PIPE-потока; порядок применения не важен, но правку лучше делать одной.

## Goals / Non-Goals

**Goals:**
- Ни один байт вывода emerge не способен остановить прогон: декодирование всегда завершается, `rc` возвращается.
- Детерминированная, зафиксированная в спеке политика обработки недекодируемых байт.
- Не деградировать читаемость там, где вывод валиден (подавляющее большинство прогонов).

**Non-Goals:**
- Восстановление исходных байтов (обратимое кодирование) — не нужно потребителям буфера.
- Угадывание кодировки (chardet/charset detection) — недопустимо по spirit stdlib-only и недетерминированно.
- Изменение кодировки, в которой emerge-ai пишет собственный stdout.

## Decisions

### D1: `errors="replace"`, а не `surrogateescape`
- `surrogateescape` сохраняет байты обратимо, но создаёт сурогатные символы, которые летят дальше в `sys.stdout.write`, `json.dumps` (report.json!) и `build_incident` — и падают уже там, при кодировании, причём в не-UTF-8 консоли `UnicodeEncodeError` — это ровно тот же исходный баг, отодвинутый по стеку. Отдельно `report.json` пишется с `ensure_ascii=False`? — даже с `ensure_ascii=True` сурогаты недопустимы в JSON и `json.dumps` бросит.
- `replace` теряет содержимое недекодируемых байт (знак ``), но не порождает ядовитых символов: любой последующий вывод/сериализация безопасны. Для отчёта и детекта паттернов инцидента потеря нескольких байт имени файла безвредна.
- Гибрид (surrogateescape в буфер, replace при печати) — два представления одного текста, рассинхрон ассертов; отвергнуто ради одного инварианта: «в тексте захвата нет сурогатов».
- Альтернатива из REVIEW_NOTES — буквально `text=True, errors="replace"` в `subprocess.run`; принимается как реализация, спецификация же фиксирует поведение, а не аргумент.

### D2: политика живёт в console-output, не в новом capability
Декодирование — часть контракта «как вывод emerge доходит до пользователя», там же лежит захват и `--color=y` (`console-output/spec.md:83`). Только ADDED-требование «Толерантное декодирование вывода emerge»: базовая фраза «вывод emerge передаётся без изменений» (`console-output/spec.md:84`) формально остаётся в силе для декодируемого вывода, конфликт закрывается сценарием нового требования («валидный вывод не затронут»); переписывать чужое требование из-за одной оговорки — лишний MODIFIED-шум.

## Risks / Trade-offs

- Пользователь теряет оригинальные байты «?»-заменой: имя файла может стать нечитаемым. Принято осознанно — обратная цена (обрванный прогон без rc) хуже; raw-passthrough путь (`run_emerge`) остаётся байтово-точным.
- Расхождение с `split-emerge-stderr`: обе правки трогают `run_emerge_capturing`. Порядок любой; tasks этой серии не предполагают слияния потоков обратно.

## Migration Plan

Пользовательской миграции нет; поведение меняется с «падает» на «печатает с заменой». Тесты: стаб с байтом `\xff` в имени пакета.
