# Design

## Context

См. proposal.md — Why. Текущее состояние, важное для решения:

- `run_tool_loop` (llm.py) уже умеет cycle «model → tool → model» и дописывает результаты инструментов как `role=tool` сообщения — ответ оператора ложится в этот же механизм без нового цикла.
- `gate.gate()` (gate.py) — реализованный, но не подключённый consent-gate **применения** вариантов (Variant.action = мутация, audit). Это другой сценарий: там варианты исполняются, здесь — уточняют разбор.
- Директива «never wait for the answer» + маркеры живут в склейке системного промпта `IncidentAgent.propose()` (agent.py); интерактивность нигде в агенте не выражена, `_maybe_agent` вызывается из трёх веток сбоя `cli.main`.
- Тесты гоняют агента через `ScriptedClient` (test_agent.py) — seam для ввода должен быть таким же инъектируемым.

## Goals / Non-Goals

**Goals:**
- Один вопрос за разом, варианты с последствиями, свободный текст, quit; ответ влияет на финальный proposal.
- Структурная (а не промптная) невозможность задать вопрос вне интерактива.
- Гарантированные выходы (quit/EOF/лимит) — отсутствие зависаний.

**Non-Goals:**
- Применение выбранного варианта, apply-канал, `gate.gate()` в prod-пути — отдельное изменение.
- Диалог об успехе: опрос только на ветках сбоя; `Proceed? [y/N]` и etc-update-промпты не трогаем.
- Сохранение стенограммы диалога между запусками; журнал (`journal`) не меняется.

## Decisions

### D1: вопрос — инструмент в существующем tool-цикле, а не gate-подобный цикл после proposal
`ask_operator` — новый tool-spec в `TOOL_SPECS`, включаемый в payload только в интерактиве. Модель может спросить в любой момент разбора (до/между pretend-проверками), ответ возвращается тем же каналом `role=tool`, цикл продолжается. Альтернатива — вызывать `gate.gate()` после финального proposal: отвергнуто, потому что gate — канал мутаций с `action()`-колбэками, варианты модели не исполняются (Non-Goal), и вопрос «какой init?» после исчерпанного proposals всё равно бы остался без канала.

### D2: интерактивность вычисляется один раз в `cli.main` и решаем включением инструмента
`interactive = not pretend and not mode.noninteractive and sys.stdin.isatty()`. Проброс: `cli.main` → `_maybe_agent(..., interactive)` → `IncidentAgent.propose(incident, render_to=..., interactive=...)`. В не-интерактиве инструмент не включается в `tools` payload вовсе — гарантия структурная, модель не может «договориться» дождаться ввода; промптные директивы лишь экономят бюджеты. Альтернатива — проверка TTY внутри dispatch при каждом вызове: модель тратила бы бюджет на заведомо провальный вызов и училась игнорировать промпт.

### D3: канал ввода — инъектируемый callable с дефолтом
`IncidentAgent(..., ask_channel=None)`; дефолт печатает вопрос через `ui.render_question` в `sys.stderr` (agent-вывод всегда в stderr) и читает `input()`. Тесты подсовывают scripted-канал. `EOFError` из ввода трактуется как quit; после первого «нет ответа» агент ставит флаг — последующие `ask_operator` возвращают `{"status":"no-answer"}` без печати.

### D4: один вопрос за разом — per-round guard
Dispatch ведёт счётчик: второй вызов `ask_operator` в том же ходе модели получает `{"error":"one question at a time"}` без показа вопроса. Последовательный dispatch в run_tool_loop даёт и наблюдаемое «следующий вопрос только после ответа». Промпт директивно требует один вопрос на вызов.

### D5: схема вопроса и валидация в dispatch
`ask_operator(question, options[{label, consequences}])`; 1–6 вариантов, непустые поля; невалидная схема → `{"error": ...}` с подсказкой, бюджет вопроса не тратится. Бюджет: максимум 3 показанных вопроса за разбор; превышение → `{"status":"no-answer","reason":"limit"}` с требованием завершиться с допущениями. Ответ: `{"status":"answered","choice":"<текст варианта>"}` или `{"status":"answered","free_text":"<дословно>"}`; `[c]`/свободный ввод без распознавания номера — свободный текст.

### D6: рендер — `ui.render_question(question, options, palette, stream)`
Строка вопроса — question-цвет палитры `llm_colors`; варианты и их последствия — content-цвет; строка выбора (`[1..n], [c] свой текст, [q] выйти: `) — стиль `ui.prompt`. Цвет — по действующим правилам `console-output` (TTY+NO_COLOR+TERM), в pipe — plain. Ответ/выбор эхом печатается сразу после ввода, чтобы стенограмма разбора читалась.

### D7: маркеры упраздняются, assumptions получают явный заголовок
Из склейки промпта убираются «never wait for the answer» и `QUESTION:`-директива; вместо них режимная: в интерактиве — «если факт известен только оператору — ask_operator, варианты обязаны быть проверены pretend_emerge и содержать последствия»; в не-интерактиве — «не спрашивай; заверши proposal секцией `ASSUMPTIONS:` со списком допущений». Заголовок `ASSUMPTIONS:` — текстовое соглашение (тестируется ассертом промпта), раскраску не получает. Подсветка `QUESTION:` в ui/console-output остаётся как display-политика без промптной генерации.

### D8: ответы оператора — доверенный вход
Оператор — субъект согласия; `injection.wrap_untrusted` на ответы не навешивается (иначе модель будет параноить на «rm -rf всё» из клавиатуры оператора, что ломает сценарий собственного текста). Вызовы и ответы пишутся в `result.trace` для тестов; в run store стенограмма не кладётся (YAGNI, см. Open Questions).

## Risks / Trade-offs

- [Локальная недетерминированная модель игнорирует tool или спамит вопросами] → структурные ограничители (D2 включение, D4 guard, D5 лимит) работают независимо от промпта; unit-тесты на scripted-клиенте, live-проверка только в integration-реплеях.
- [Строки ответа «утекают» в stdin дочернего emerge при pretend_emerge] → вопросы печатаются только между вызовами инструментов, emerge-подпроцессы (pretend) stdin не читают; риск остаётся только от «печатания наобум» и безвреден (стрки съедаются `input()` опроса следующим же вопросом).
- [TTY-скрипты без `-a` раньше падали сразу, теперь ждут ввод] — это и есть цель изменения; `--noninteractive`/pipe сохраняют прежнее поведение. BREAKING зафиксирован в proposal/spec-дельте.
- [Наводящий вопрос, сгенерированный injection-данными из логов] → варианты показываются оператору с последствиями и проверками; мутаций опрос не делает; модель обязана ссылаться на pretend-проверку варианта (частично митигируется, полностью — нет, как и весь proposal).
- [Тесты CLI с stdin-инъекцией усложняются] → `agent_fn`-seam `_maybe_agent` расширяется именованным параметром с обратимо-дефолтной сигнатурой; юнит-клиент-тесты не трогают настоящий TTY.

## Migration Plan

Код: обычная коммит-последовательность из tasks.md; откат — revert (ни migrated-файлов, ни нового конфига). Конфиг `emerge-ai.json` не меняется. Поведение в `-p`/`--noninteractive`/pipe — обратная совместимость по умолчанию.
