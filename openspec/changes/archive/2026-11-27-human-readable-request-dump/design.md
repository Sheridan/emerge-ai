# Design

## Context

`LLMClient._dump_request` (`src/emerge_ai/llm.py:87-94`) сериализует payload целиком
(`json.dumps`), вырезает значение API-ключа подстановкой и режет результат `ui.clip` по
`REQUEST_DUMP_LIMIT = 8000`; `chat()` печатает всё это одной строкой через `_announce`.
Содержимое payload типичного agent-вызова: системный промпт (десятки килобайт: правила +
скелет класса инцидента + whitelist вариантов), user-сообщение с текстом инцидента, далее
ходы ассистента с tool-call'ами и `tool`-сообщения с результатами инструментов (JSON-текст до
`MAX_TOOL_RESULT_CHARS`). То есть первые 8000 символов дампа почти всегда занятые системным
промптом, а интересующие tool-call'и в него не попадают.

Все служебные строки stderr появляются через `ui.activity` (префикс `emerge-ai: `, без цвета
даже в TTY — см. spec `progress-logging`/`console-output`), stdout остаётся passthrough
emerge. Тестовый шов `chat()` — заглушка `urllib.request.urlopen` (`tests/test_llm.py`).

Зависимость порядка применения: capability `progress-logging` описана в незаархивированном
`add-progress-logging`; её требование «Детальные логи при -v» — то, что правит этот delta.

## Goals / Non-Goals

**Goals:**

- Дамп читается глазами и grep'ом: один логический элемент payload — одна строка.
- Формат устойчив к росту payload: неизвестные поля получают тот же вид, что и известные.
- Видно, где текст усечён, и какого он был размера.
- Дамп остаётся в stderr, plain в pipe, без значений аутентификации.

**Non-Goals:**

- Machine-readable дамп запроса (флаг/ключ конфига для JSON), дампы в файл, дампы ответов
  эндпоинта.
- Изменение анонса запроса, строки длительности, поведения без `-v`, контракта `chat()` и
  tool-цикла.
- Окраска дампа (он info-стиля, как остальные строки активности) и `-vv`.

## Decisions

**D1. Рендер — чистая функция в `ui.py`, не метод `LLMClient`.**
`ui.render_request(payload, api_key=None, field_limit=…, total_limit=…) -> list[str]`
возвращает готовые строки; `llm.py` лишь печатает их по одной через `_announce`. `ui.py` уже
владеет оформлением (`activity`, `clip`, `paint_llm_block`), а рендер без HTTP-заглушки
тестируется прямыми фикстурами payload. Альтернатива — приватный метод `_render_request` в
`LLMClient` — проверялась бы только через заглушку `urlopen` и смешала бы транспорт с
оформлением.

**D2. Строки блока (каждая — строка активности со своим префиксом, отступ после префикса):**

```
emerge-ai: request: model=qwen3.8-… temperature=0.2 messages=4 tools=7 body=18 213 chars
emerge-ai:   [1] system · 9 412 chars: You are an assistant for Gentoo… [capped, 9 412 chars]
emerge-ai:   [2] user · 1 204 chars: Incident context follows… [capped, 1 204 chars]
emerge-ai:   [3] assistant · tool_calls: pretend_emerge(category=app-editors/vim)
emerge-ai:   [4] tool call_0fef95 · 6 900 chars: ok=True · stderr_tail="!!! PORTAGE…"[capped]
emerge-ai:   tool[1/7] pretend_emerge — simulate an emerge run (args: category, flags)
```

Префикс на каждой строке сохраняет инвариант «все служебные строки stderr — с `emerge-ai: `»
и делает блоки различимыми в интерливинге с выводом emerge. Альтернатива (общий префикс на
заголовок, тело без префикса) ломает этот инвариант и путает при `grep 'emerge-ai:'`.

**D3. Два капа вместо одного.**
`DUMP_FIELD_LIMIT = 400` на текстовое значение и `DUMP_TOTAL_LIMIT = 4000` на блок целиком;
плашка усечения — та же, что в `ui.clip` (`…[capped, N chars total]`), плюс итоговая строка
`dump truncated: shown 21 of 63 lines`. Однострочный кап на весь дамп (нынешние 8000)
съедается первым же системным промптом — именно это и чиним; общий кап при этом всё ещё
нужен, чтобы сотня сообщений не растянула терминал. `REQUEST_DUMP_LIMIT` заменяется этими
двумя константами.

**D4. Значения рендерятся типом, а не сериализацией.**
Скаляр — как есть; `dict` — `k=v` через запятую, при вложенности глубже одного уровня
продолжение следующей строкой с отступом; `list` — элементы с индексом (`arg[1]=…`).
Строка, которая является JSON-текстом (так приходят результаты инструментов), перед
оформлением парсится и рендерится теми же `k=v`; не парсится — печатается как текст.
Переводы строк внутри текстов сворачиваются в `⏎`, чтобы один элемент = одна строка.
Неизвестные поля payload попадают в тот же обход, поэтому новый ключ не может превратить дамп
в JSON — это отдельный сценарий spec.

**D5. Секреты маскируются построчно, после рендера.**
`api_key` вырезается подстановкой в каждой готовой строке (как сейчас в JSON-строке), плюс
полное совпадение значения поля значению ключа. Размеры в `N chars` считаются по исходному
значению — иначе плашка врёт о размере. Заголовки (`Authorization`) в дамп не попадают: их
нет в payload, и добавлять их в рендер нельзя.

**D6. Место и количество дампов не меняются.**
Один блок на `chat()`, сразу после `sending request to LLM (...)`, до `LLM answered in …` —
порядок фиксирует существующий тест `test_chat_announces_request_then_answer`. Строка
длительности остаётся как есть.

**D7. Тесты оформителя — над фикстурами, интеграция — над `-v`.**
`test_ui` покрывает `render_request` на фикстурах (system+user, tool_calls, длинный
tool-результат, неизвестное поле, значение == api_key, многострочный текст); `test_llm` —
что при `verbose=True` в stderr есть строки `request:` и `[1] system`, нет `{`/`}`-блоков и
значения ключа, при `verbose=False` нет ничего; `test_cli` — что `--pretend -v` прогон не
выдаёт сериализованный JSON в stderr.

## Risks / Trade-offs

- Теряется «скопируй и отправь curl'ом» → содержательные поля остаются видны полностью или с
  явной плашкой; точный побайтовый payload при необходимости берётся из логов эндпоинта,
  восстановление machine-readable дампа — явный Non-Goal.
- Превью скрывает середину больших текстов → плашка с исходным размером; кап поля 400
  символов сохраняет суммарный дамп заметно короче нынешних 8000.
- Нестандартные формы payload (`content` списком частей, `null`, числа с `NaN`) →
  тип-ориентированный обход D4 плюс сценарий «неизвестное поле»; на худой конец значение
  печатается текстом, но не JSON-синтаксисом.
- Больше строк на запрос → шум в длинном tool-цикле; ограничение D3 и отсутствие дампа без
  `-v` ограничивают объём.
- Delta правит требование capability, ещё не попавшей в `openspec/specs/` → применять после
  синка/архивации `add-progress-logging`, иначе архив не найдёт, куда накатывать изменение.

## Migration Plan

Реализация — `ui.render_request` + переработка `_dump_request`/`chat()`, затем тесты и
документация (`README.md`, `LIVE_CHECKS.md`). Конфигурация и форматы на диске не меняются,
откат — revert коммита изменения; внешние потребители дампа (люди и grep) теряют прежнюю
строку `request payload: {…}`, что и зафиксировано как BREAKING в proposal.
