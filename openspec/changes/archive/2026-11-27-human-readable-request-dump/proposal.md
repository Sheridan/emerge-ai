# Proposal

## Why

`-v` печатает тело запроса к эндпоинту одной строкой `json.dumps` (`llm._dump_request`,
cap 8000 символов): в терминале это стена `{"model": "…", "messages": [{"role": "system",
"content": "You are …`, где системный промпт и JSON-схемы инструментов занимают почти весь
кап, а именно их видеть и не нужно. В итоге при разборе прогона нельзя ответить на вопрос
«что именно ушло модели»: нужный tool-call или аргумент тонут в экранированных кавычках,
многострочные содержимые сообщений свёрнуты в `\n`, дамп невозможно прочитать глазами и
нельзя grep'ом по смыслу.

## What Changes

- Дамп запроса при `-v` перестаёт быть JSON. Вместо одной строки — построчный
  человекочитаемый блок: заголовок (model, temperature, число сообщений, число tools,
  размер тела), затем по одной строке на сообщение (`[2] user · 312 chars · <превью>`),
  отдельно tool-calls ассистента (`→ tool pretend_emerge(args=…)`), отдельно результаты
  инструментов и отдельно список инструментов с описаниями.
- Вложенные значения выводятся парами `key=value`/подстроками с отступом; синтаксис JSON
  (фигурные скобки, кавычки-экраны, `\"`) в дампе не появляется ни для известной, ни для
  неизвестной части payload.
- Капы пересмотрены: отдельный кап на текстовое поле и отдельный на весь дамп, каждый с
  явной плашкой и исходным размером, чтобы усечение было видно, а не молчаливым.
- **BREAKING (формат вывода, не API)**: строка `request payload: {…}` уходит;
  machine-readable дамп запроса взамен не предоставляется — флага или ключа конфига,
  возвращающего JSON, нет и не добавляется.
- Без изменений: дамп только при `-v`, только в stderr, маскирование API-ключа, заголовок
  `Authorization` не дампится, plain-текст в pipe, коды выхода и passthrough emerge.

### Modified Capabilities

- `progress-logging`: требование «Детальные логи при -v» переписывается (тело запроса
  показывается человекочитаемым блоком, а не JSON) и добавляется требование
  «Человекочитаемый дамп запроса» с контрактом оформления, капов и маскирования.

> Зависимость: `progress-logging` ещё не попала в `openspec/specs/` — изменение
> `add-progress-logging` завершено, но не заархивировано. Delta правит требование из
> `openspec/changes/add-progress-logging/specs/progress-logging/spec.md` (текст скопирован
> целиком), поэтому применять изменение следует после синка/архивации `add-progress-logging`.

## Impact

- `src/emerge_ai/ui.py` — рендер человекочитаемого дампа (чистая функция payload → строки),
  рядом с `activity`/`clip`; окраска не нужна, дамп info-стиля.
- `src/emerge_ai/llm.py` — `_dump_request` возвращает строки, `chat()` печатает их через
  `_announce` по одной; константы капа (`REQUEST_DUMP_LIMIT` → кап поля + кап дампа).
- Тесты: `test_ui` (рендер по фикстурам payload), `test_llm` (дамп при `-v`, отсутствие
  JSON-синтаксиса, маскирование ключа, plain в pipe), `test_cli` (`-pv` не содержит `{`).
- `README.md` (раздел «Прогресс прогона и `-v`»), `LIVE_CHECKS.md` (шаг 2 секции
  `add-progress-logging`).
- Пересечение с `stream-llm-output-live`: тот же `LLMClient.chat()`, но аспекты независимы
  (формат дампа против времени показа ответа), порядок применения любой.
