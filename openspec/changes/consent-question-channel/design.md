# Design

## Context

Спекa `consent-dialogue` требует: свободный текст оператора уходит «в тот же контекст
разбора», агент «ответит/уточнит/перестроит варианты». Фактически `consent_analyze` (cli.py)
делает один JSON-only вызов `CONSENT_ANALYSIS_SYSTEM` («using only facts from the input») без
истории и без инструментов, а чтение ответа опирается на dict-контракт (`resp.get("choices")`)
там, где `LLMClient.chat` возвращает dataclass `Response` — вопрос оператора уронил весь
запуск (`AttributeError`, не пойманный `except LLMError`). Цель проекта — помогать оператору
добиваться установки пакетов; consent-диалог должен быть советником «как сделать, чтобы
запрошенное установилось», помнящим свои прежние реплики.

Смежные готовые механики: `run_tool_loop` (llm.py, tool→model до контент-ответа,
`LimitExhausted` при `finish_reason=length`/исчерпании раундов), read-only `TOOL_SPECS` +
исполнители `Sandbox` (agent.py: `read_file_window`, `grep_log`, `journal_search`,
`web_fetch`, `pretend_emerge`, `check_world`), инвариант мутации — только номер через
`gate.apply_variant`, разбор `{comment, order}` через `parse_analysis` (уже деградирует к
сырому тексту), `news.parse_digest` — эталонный «любая форма ответа» seam.

## Goals / Non-Goals

**Goals:**
- диалог: история сообщений живёт между раундами consent-цикла, сжимается у лимита;
- ответ на текст оператора — до и вместо отказа «фактов во входе нет»; при нехватке фактов
  канал читает логи/journal/world и ходит в web read-only инструментами;
- ни один сбой канала (любое исключение) не прерывает запуск — заметка над меню;
- схема `{comment, order}` и инвариант «мутация только по номеру» не двигаются.

**Non-Goals:**
- параллельный/фоновый канал (синхронный раунд, как сейчас);
- новый whitelist исполняемых действий;
- streaming-оформление ответа (уже покрывается llm-streaming при `-v`).

## Decisions

### D1. Класс состояния диалога в consent.py, cli собирает его один раз

`ConsentDialogue(client, *, language, sandbox, max_rounds=6)`: держит `messages` (system +
раунды), метод `analyze(text, specs) -> (comment, order)` — подпись seam'а `run_dialog`
не меняется. cli строит объект один раз до `while True` consent-цикла: история переживает
раунды и пересборку меню после применённой починки. Альтернатива (замыкание-/nonlocal в
cli) отвергнута: логика истории/сжатия должна тестироваться без cli.

### D2. История раундов + детерминированное сжатие

Каждый раунд кладёт в историю реплику оператора и content-ответ модели (tool-обмен
раунда — целиком: assistant+tool_calls/results, модель сама видит, чем пользовалась).
Перед вызовом, если сериализованная история превышает бюджет (порядка 24k символов),
старые раунды, кроме последних 2, сворачиваются в один system-дайджест: применённые
починки (`run.consent_repairs`), версии очередей, первые строки прежних ответов. Сжатие
детерминированное (без LLM-резюмирования) — по духу кодовой базы, дёшево, воспроизводимо
в тестах. `LimitExhausted` из loop → заключительный раунд без инструментов: к накопленному
tool-обмену добавляется директива `TOOL_STOP_DIRECTIVE` и один `chat` без tools (живая
калибровка задачи 5.1: эндпоинт тратит бюджет продуктивно, выброшенный бюджет не должен
выбрасывать собранную доказательную базу). Если и он падает — та же деградация, что и
сбой канала (ответ-основка не теряется: `partial` не показываем, чтобы не печатать
обрезанный JSON).

### D3. Промпт: сначала ответ, потом порядок; JSON-схема прежняя

Новый `CONSENT_ANALYSIS_SYSTEM`: советник по установке; сначала ответить на текст
оператора (вопрос/уточнение/предложение), опираясь на вход и, когда фактов не хватает,
на read-only инструменты (логи сборки, journal, world, `pretend_emerge`, web); затем,
если ответ меняет полезность вариантов, упорядочить известные ключи. Ровно один JSON
`{"comment": ..., "order": [...]}` — `parse_analysis` не меняется, комментарий-сырой-текст
деградирует как раньше. Запрет выдумывать действия/ключи сохраняется дословно.

### D4. Инструменты: подмножество TOOL_SPECS без `ask_operator`, свой dispatch

Консенс-канал получает `read_file_window`, `grep_log`, `journal_search`, `web_fetch`,
`pretend_emerge`, `check_world` — dispatch поверх тех же методов `Sandbox`
(agent._dispatch переиспользовать как метод whole-объекта нельзя: он завязан на
AgentResult/interactive-гейтинг), `ask_operator` исключён — оператор уже в диалоге,
его текст и есть канал вопросов. Песочница: `DEFAULT_JAIL_ROOTS` + каталог artifact'а
план-фазы (как в pretend-ветке cli). Исполняющих инструментов нет — инвариант spec'ы.

### D5. Ответ канала читается через общий seam, сбой — всегда деградация

В llm.py появляется `response_text(result)` (dict-контракт / `Response` / строка),
`news.parse_digest` приводит себя к нему же. `ConsentDialogue.analyze` оборачивает весь
раунд в `except Exception` → `(заметка, [])`: меню перерисовывается, запуск жив. Именно
отсутствие этой границы убило прогон с `AttributeError`.

## Risks / Trade-offs

- Latency раунда растёт (инструментальные ходы до 6 раундов) — осознанная цена: сейчас
  канал либо врёт «фактов нет», либо падает.
- История + инструменты размывают «дешёвый разбор» consent: бюджет сжатия и max_rounds
  ограничивают стоимость; меню и выходы (q/EOF/ctrl-c) не зависят от канала.
- Модель может ответить, но не вернуть валидный JSON → `parse_analysis` печатает сырой
  текст как комментарий: порядок не меняется, диалог продолжается.
- web_fetch в consent-канале расширяет read-only поверхность на сеть — уже разрешено
  agent-петле; sandbox-капы и аудит те же.

## Migration Plan

Обычная выкатка. `analyze`-seam `run_dialog` сохраняет подпись — сторонних потребителей
нет (consent строит канал сам). Откат — предыдущая версия.

## Open Questions

- Точный бюджет истории (24k символов как ориентир) — живой прогон 2026-11-27 двух
  раундов до бюджета не довёл; ориентир оставлен. Реальной калибровкой оказалось
  другое: эндпоинт тратит весь tool-бюджет продуктивно, поэтому добавлен
  заключительный раунд без инструментов (D2, правка по итогам задачи 5.1).
