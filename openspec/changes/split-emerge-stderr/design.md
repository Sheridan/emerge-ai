# Design

## Context

- Захват один на все сценарии: `run_emerge_capturing` (`runner.py:32-50`) вызывается из plan-фазы (`cli.py:333`) и merge под `-a` (`cli.py:410`); буфер идёт в `build_incident`, `hooks.run_hook`, `digest.parse_installed`.
- Слияние `stderr=STDOUT` выбиралось, чтобы не мертлоковать два PIPE-канала простым циклом по строкам; это единственный мотив слияния (M2 в REVIEW_NOTES прямо называет компромисс неизбежным — буфер нужен).
- Строгий контракт на возвращаемое: `(int, str)`; менять его — значит править все ветки `cli.main`, чего меняться не должно.

## Goals / Non-Goals

**Goals:**
- stdout emerge-ai содержит только stdout emerge (байт-в-байт, ANSI как есть); stderr emerge уходит в stderr emerge-ai.
- Единый буфер для incident/enrich/hooks сохраняется; сигнатура функции не меняется.
- Мертлока нет при полноэкранном выводе в оба потока.

**Non-Goals:**
- Точный межпотоковый порядок в буфере (не гарантируется и не проверяется).
- `run_emerge` (raw-passthrough, наследует stdio) не меняется.
- Детект «какая строка на самом деле ошибка» по префиксам — не делаем.

## Decisions

### D1: два потока чтения на потоках, а не `stderr=STDOUT` с постразбором
В `run_emerge_capturing` два daemon-потока: каждый читает свой PIPE построчно, пишет в соответствующий `sys.stdout`/`sys.stderr` (flush) и дописывает ANSI-stripped-строку в общий буфер под `threading.Lock`. Альтернатива — оставить слияние и различать потоки по префиксам portage: отвергнуто, у portage нет стабильного маркера stderr-строк (M2), эвристики будут ошибаться и на крашеных строках. Альтернатива `asyncio`/`selectors`: рабочая, но тянет перестройку функции на событийный цикл ради задачи, которую два `readline`-цикла решают нативно.

### D2: буфер — плоский текст, порядок «по прочтению»
Общий `list[str]` + лок; `join` после `proc.wait()`. Гарантируется только полнота строк, не чередование потоков. Для потребителей это приемлемо: `build_incident` ищет паттерны по всему тексту, `parse_installed` матчит строки `>>> Emerging`/`[ebuild` (stdout portage), `hooks` получает тот же текст, что и раньше. Альтернатива — возвращать два буфера `(rc, out, err)`: точнее, но ломает контракт и всех вызывающих; не нужно ни одному текущему потребителю.

### D3: окраска и `--color=y` не трогаем
`with_color_flag` (`runner.py:19-29`) решает окраску по `sys.stdout` emerge-ai и остаётся как есть; stderr emerge красится тем же `--color=y` и зеркалится без изменений, `ui.strip_ansi` применяется только к копии в буфер (как сейчас, `runner.py:48`).

## Risks / Trade-offs

- Порядок строк в буфере может отличаться от прежнего «строго чередующегося» — минимизируется тем, что оба потока читаются параллельно, а не последовательно (последовательное чтение deadlock'нуло бы).
- Порты consumers, парсившие stderr из stdout, увидят «исчезновение» строк — это и есть цель изменения; фиксируется в REMOVED-ожидании через новое требование спека и в tasks (README/LIVE_CHECKS).
- Два потока чтения — два места, где исключение может утонуть; потоки складывают ошибки в общий slot и пробрасывают после `wait()` (не глушим).

## Migration Plan

Код-потребители буфера не меняются; скрипты, полагавшиеся на слияние, получают корректное поведение после релиза. Миграция — только в тестовых стабах emerge (писать в оба потока различимо).
