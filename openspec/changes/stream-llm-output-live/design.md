# Design

## Context

`LLMClient.chat()` (`src/emerge_ai/llm.py:96-145`) отправляет payload и делает
`json.load(resp)` — ответ arrives целиком; `[reasoning]` печатается уже после получения,
`content` — через `render()` (её зовёт `run_tool_loop`, если задан `render_to`) либо
самостоятельными callers. Прямые вызовы (`etcupdate.llm_decide`, сводка дайджеста, news,
consent-анализ, changelog) читают `resp.content` программно и показывают его по-своему;
`cli._maybe_agent` дополнительно печатает `agent proposal:` + текст финального ответа, из-за
чего под `-v` финальный текст уже сегодня виден дважды (один раз из tool-цикла, второй —
блоком предложения).

Живой эндпоинт стенда (OpenAI-совместимый, см. прогон SSE в рамках этого изменения) отдаёт:
строки `: keep-alive`, `data: {chunk}` с `choices[0].delta.{reasoning_content,content}`,
`delta.tool_calls[]` с `index` и нарастающими фрагментами `function.arguments`, чанк с
`finish_reason` и `usage`, терминатор `data: [DONE]`. `_parse` уже умеет разбирать цельный
ответ, включая fallback `{"_raw": …}` для неразбираемых аргументов инструментов.

Тестовый шов — заглушка `urllib.request.urlopen`, возвращающая объект-контекст поверх
`io.BytesIO` (`_StubHTTP` в `tests/test_llm.py`): для потоковой ветки достаточно добавить
итерацию по строкам.

## Goals / Non-Goals

**Goals:**

- Первый текст рассуждений виден через секунды после анонса, а не после полной генерации.
- Потоковый и однократный ответы дают идентичный `Response` — tool-цикл и структурные
  consumers о режиме не знают.
- Каждый ход модели показан ровно один раз.
- Эндпоинт без стриминга работает как сегодня, цена попытки — один повтор.

**Non-Goals:**

- Стриминг без `-v`, стриминг вывода emerge и tool-результатов, параллельные вызовы.
- Новые ключи конфига и флаги, ретраи по HTTP-ошибкам, изменение промптов и `-v`-семантики.
- Изменение палитры `llm_colors` и правил `console-output` (стриминг им подчиняется).

## Decisions

**D1. Одна точка входа: ветка стриминга внутри `chat()`.**
`payload["stream"] = True` (+ `stream_options.include_usage`), затем `_stream_request(payload)
-> tuple[Response, bool]` (второй флаг — «что-то уже показано»). Публичные сигнатуры
`chat()`, `render()`, `run_tool_loop()` не меняются. Альтернатива — отдельный `chat_stream()`
— задублировала бы анонсы, длительность, `LimitExhausted` и откат, и заставила бы править все
call-sites.

**D2. Включатель — `self.verbose`, не конфиг.**
Решение пользователя: стримим только там, где рассуждения вообще показываются. Стриминг без
показа добавил бы сетевой риск без выгоды, а ключ `stream` в конфиге конфликтует с `-v` и
создал бы четвёртое состояние. Проверка стриминга остаётся в одном месте — там же, где
решение печатать `[reasoning]`.

**D3. SSE-парсер — цикл по строкам ответа, без новых зависимостей.**
`for raw in resp:` + `raw.decode("utf-8", "replace")` (то же толерантное декодирование, что
`console-output` требует для вывода emerge); пустая строка — граница события, `:`-строки
(keep-alive) и неизвестные поля игнорируются, `data: [DONE]` — конец, тело чанка —
`json.loads`. Исключение на одном чанке → чанк пропускается (счётчик), поток продолжается:
испорченный чанк не должен ронять прогон ради потерянного слова. Альтернатива — ручной
`read()`-цикл с поиском границ — избыточна: urllib-ответ итерируется по строкам сам.

**D4. Аккумулятор = `_parse`, развёрнутый во времени.**
`content`/`reasoning` — конкатенация дельт; tool-call'ы — таблица по `index` (`id`, `type`,
`function.name` — первое непустое, `function.arguments` — конкатенация), в конце `json.loads`
с тем же fallback `{"_raw": …}`; `finish_reason` — последний непустой. Эквивалентность
проверяется свойством, а не перебором: один и тот же ответ, нарезанный на дельты, должен дать
`Response`, равный разобранному `_parse` целиком. `usage` (если пришёл) — только для строки
длительности, в `Response` не попадает.

**D5. Показ: reasoning посимвольно, content построчно.**
Дельты рассуждений пишутся сразу (`print(..., end="", flush=True)`) в цвете
`llm_colors.reasoning`. Content буферизуется до перевода строки и печатается целой строкой через
правило `QUESTION:` из `paint_llm_block`, иначе маркер вопроса приедет в одном чанке, а его
окраска — в другом, и строка выйдет разноцветной (сценарий spec). Решение о цвете принимается
один раз на вызов, переход reasoning → content завершает строку переводом, чтобы блоки не
склеивались. В pipe/`NO_COLOR`/`TERM=dumb` те же тексты, без escape-кодов (`ui.paint` уже
решает по потоку). Альтернатива — красить каждый фрагмент — даёт рваную окраску; полная
буферизация content до конца ответа — теряет смысл стриминга для ответа.

**D6. Флаг «уже показано» на `Response`.**
Аддитивное поле `displayed: bool = False`: `render()` при `displayed=True` content не
печатает (tool-цикл не дублирует живой показ), `cli._maybe_agent` под `-v` печатает заголовок
`agent proposal:` и строку-пометку о том, что текст показан выше. Существующие конструкторы
`Response(content=…, reasoning=…)` (в том числе тестовые) не меняются — значение по умолчанию
сохраняет прежнее поведение.

**D7. Откат к однократному запросу — один раз и только до показа.**
`_StreamUnavailable` бросается, если ответ не похож на поток (не тот `Content-Type`, первый
`data:` не разбирается, HTTP-ошибка/обрыв до первого `_emit`); `chat()` ловит его, печатает
одно предупреждение (только при `-v`) и повторяет тот же payload без `stream` → прежний
`_parse`. Если `_emit` уже был — исключение не конвертируется: это обычный путь `LLMError`,
повтор дал бы задублированный на экране текст. Успешный откат запоминается в экземпляре
клиента (`self._stream_supported = False`), чтобы agent-петля из десятка вызовов не платила
повтором на каждом.

**D8. Тесты — поверх SSE-заглушки `urlopen`.**
`_StubSSE(chunks)` (расширение `_StubHTTP` итерацией по строкам) позволяет проверить: порядок
появления (рассуждения → текст → строка длительности) по индексам в буфере; эквивалентность
сборки `_parse`; склейку tool-call'ов с двумя индексами; `finish_reason=length` →
`LimitExhausted`; отсутствие `text/event-stream` → ровно один повтор без `stream` + одно
предупреждение; обрыв после эмита → `LLMError` без повтора (`urlopen` вызван один раз);
испорченный чанк; окраску в TTY и plain в pipe; отсутствие дублей в `run_tool_loop`.

## Risks / Trade-offs

- Эндпоинт не понимает `stream_options.include_usage` и отвечает 400 → откат D7 на однократный
  запрос; поле отправляется только в потоковой ветке.
- Интерливинг с выводом emerge: live-текст идёт в stderr, stdout остаётся побайтовым
  passthrough — смешения нет; незавершённая строка потока завершается переводом перед
  следующей строкой активности.
- Поток «медленнее» однократного запроса на накладные расходы парсинга чанков → на локальном
  стенде генерация-dominated, разница в шуме; выигрыш — время до первого текста.
- Обрыв после частичного показа оставляет на экране незавершённый fragment без повтора →
  осознанный выбор spec; строка `LLM request failed:` остаётся маркером обрыва.
- Исправление двойного показа proposal меняет привычный `-v` вывод (было два блока) →
  зафиксировано как требование «однократный показ», пометка в блоке предложения сохраняет
  различимость финального текста.
- Модели без reasoning не дают дельт `reasoning_content` → печатается только текст, сценарии
  с рассуждениями просто не срабатывают.

## Migration Plan

Порядок: аккумулятор + SSE-парсер с тестом эквивалентности (D3/D4) → показ по дельтам (D5) →
флаг `displayed` и правка `cli._maybe_agent` (D6) → откат (D7) → документация (`README.md`,
`LIVE_CHECKS.md`). Откат изменения — revert: поведение без `-v` не затрагивается, данные и
конфиг не меняются.

## Open Questions

- Нужен ли отдельный лимит на длину живого вывода рассуждений (сейчас ограничено только
  объёмом генерации модели) — решается по факту наблюдаемого шума, на спеки не влияет.
- Показывать ли `usage`-токены в строке длительности всегда или только при потоковом режиме —
  косметика, проверяемая тестом строки.
